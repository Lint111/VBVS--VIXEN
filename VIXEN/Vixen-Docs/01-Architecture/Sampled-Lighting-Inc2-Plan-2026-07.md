# Sampled Lighting Inc2 — Temporal Accumulation — Plan (2026-07)

**Spec:** `Sampled-Lighting-Design-2026-07.md` §4 (Inc2 roadmap line), §5 (pipeline: shade → temporal accumulation → [denoiser later] → tonemap/UI), §6 open-decision #5 (body motion vectors — deferred), bias-ledger table row "Temporal accumulation: consistent when static; ghosting when moving → reprojection validation".

**Base:** main `5e0b4f38` (Inc0 + Inc1 merged + pushed to origin).

**Scope:** temporal reuse of prior-frame shaded radiance to drive variance → 0 on static views (the prerequisite for every stochastic layer that follows — Inc3 ReSTIR, Inc4 DDGI, Inc5 specular all lean on a stable history). Camera-only-motion reprojection with per-pixel history validation; body-motion reprojection explicitly DEFERRED (design §6 #5). EWMA history with a hard-reset escape hatch that reproduces Inc1 output exactly.

## KI-018 status: **Inc2 is UNBLOCKED** (scouted, code-grounded)
Temporal accumulation does NOT need the separate `DirectLighting.comp` pass that KI-018 defers. It slots in **in-place** at the tail of the existing inline shading in `BodyInstanceRayMarch.comp` — immediately before `imageStore(outputImage, …)` (`:1291`): read `history[pixel]`, blend `outColor = mix(history, outColor, alpha)`, write back to both `outputImage` and `history`. It needs NONE of the ~9 scene SSBOs that made a separate shadow/GI pass exceed `ComputeStageNode`'s 3-hazard-slot cap — it rides inside the march dispatch that already binds them. (If ever split out later, its footprint — history-in + current-in + blended-out — fits the cap anyway; accumulation is the ONE lighting layer that does.) It is Inc3 ReSTIR, not Inc2, that owes the RenderGraph library change.

**The one genuinely-new engine piece:** history must be a PERSISTENT storage image that survives across frames — NOT the `RenderTargetNode` ring, which rotates every frame (KI-009). Inc2 adds a dedicated persistent history image + its node (a small new binding, 19+; 17=HitRecord, 18=ShadowConfig taken). Well within existing StorageBufferNode/RenderTargetNode patterns but not a copy-paste of either — budgeted in M1.

**Not reusable:** the existing `AccumulationConnectionRule`/`AccumulationSortConfig`/`test_accumulation_gather` machinery is a graph-connection-time single-frame fan-in (merge N producer connections → one `vector<T>` at a consumer slot) — no GPU images, no cross-frame persistence. Naming collision only; ignore it. Inc2 builds its own history image.

## Self-Review
- **Why is M1 plumbing-only with a byte-identical gate?** Same discipline as Inc0 M3 / Inc1 M3 — prove the config + history-image + wiring are behavior-neutral in isolation, so any later visual change is attributable to the accumulation logic, not a plumbing regression.
- **Why static-EWMA (M2) before reprojection (M4)?** The design gate is two independent things — static convergence AND no-ghost-on-orbit. Static-EWMA + hard-reset-on-motion satisfies both trivially (reset = pure current = Inc1 = zero ghosting by construction) and gives a working noise-free static image early. Reprojection (M4) is then a pure improvement layered on top (ghost-free WHILE moving, not just reset-to-noisy) — isolating the harder, bug-prone reprojection+validation logic into its own gated milestone.
- **Why the M3 matrix-plumbing byte-identical gate between M2 and M4?** So an M4 reprojection bug can't be a hidden M3 upload regression — the matrix arrives (M3, proven neutral) before it's consumed (M4).
- **Deliberate non-scope:** no body-motion reprojection (design §6 #5 — rigid-body instance-transform reprojection is a later increment; procedural deformation is out of scope entirely); no denoiser (Inc5); no reservoirs (Inc3); no separate DirectLighting pass (KI-018, owed to Inc3 not Inc2). Accumulation stays inline in the march.
- **KI-019 acknowledged up front** — M5's cost measurement uses the FrameTimer substitute from the start, not the broken isolated-GPU-dispatch path.
