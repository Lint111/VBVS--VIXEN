# SDF Bake Box-Tight Region — Plan (2026-07)

**Trigger:** Cornell Box GI demo investigation (2026-07-14/15) found `BakeSdfWorld`/`BuildSdfBodyOctree` bake every body into a CUBE grid (single scalar `int n`, identical on all 3 axes), and confirmed this is a genuinely prohibiting problem, not just a cosmetic one: a thin body (a Cornell wall, ~2 world-units thick but 20+ units wide/tall) must be baked into a cube big enough to cover its LONG axis — wasting enormous empty volume on its THIN axis. This produces two separately-measured real costs on the SAME root cause: (1) grazing rays traverse the wasted empty span before reaching the iso-surface, reporting a legitimate-but-large `hitT`/`worldPos` (the "~35-40k out-of-bounds hits" finding from the Cornell investigation's M3 rounds 5-6 — NOT visible corruption, but real wasted traversal); (2) a decisively measured **~147× GPU performance collapse** (baked Cornell scene ~0.9 FPS vs. an equivalent procedural/analytic scene ~126 FPS, M3 round 7) — the GPU pays full trilinear brick-march cost across mostly-empty cube volume, for every thin body, every frame, for both primary rays AND DDGI probe rays. This blocks the baked Cornell variant from being usable and is a real cost tax on ANY thin/elongated stored-SDF body in this engine, not Cornell-specific.

**Base:** `main` (current HEAD `7b40ff0e` at plan-writing time — has the render-graph sync fix, the Cornell geometry+baked-path fixes, the discrete-GPU-selection fix, and the Cornell color fixes all merged).

## Grounding from codebase investigation (2026-07-15, via a dedicated Explore survey)

**The anisotropy machinery already exists end-to-end — this is what makes the fix narrow, not a ground-up redesign.** The GPU config struct (`OctreeConfig`) already carries a genuine per-axis AABB (`gridMin`/`gridMax` as `Float3`, `OctreeConfig.cs:...`, byte offsets 32/48) and a full `localToWorld`/`worldToLocal` `Mat4` (non-uniform-scale-capable) at byte offsets 64/128. Every shader consumer of world↔local transforms already applies the FULL matrix (`ESVOCoefficients.glsl:53,57`; `SceneBindings.glsl:476`) — there is no scalar shortcut anywhere in the traversal math that assumes uniform scale. `rayAABBIntersection` (`RayGeneration.glsl:81-93`) is fully per-axis. The ESVO octree descent itself IS intrinsically a cube subdivision (a single scalar halves all 3 axes per level, `ESVOTraversal.glsl:260-266`) — this is fundamental to how ESVO works and is NOT something this plan proposes to change.

**The ONLY thing hard-wired to a single cube scalar is the brick-lookup flat-index table** — on BOTH the CPU serializer (`ShellOctreeGpu.h:785-810`, `flat = gx + gy*bpa + gz*bpa²`) and the GLSL reader (`StoredSdf.glsl:32-38`, `_gridToLookupIdx`, same formula) — kept bit-identical by `test_soa_sdf_serialize.cpp:156-183`'s own parity assertions. `BakeSdfWorld`'s `int n` (`SdfBake.h:104-109`) is used identically on all 3 axes throughout the bake's two passes (`:145-147, 208-210, 219-221`); `BuildSdfBodyOctree` hardcodes `worldMin=(0,0,0)`, `worldMax=(n,n,n)` (`:351-352`) and derives the octree's actual pow2 grid as `2^floor(log2(n))` (`:356-361`, silently rounding non-pow2 `n` DOWN — the exact mechanism that caused the Cornell investigation's earlier `kWallN=112` bug). `SVORebuild::rebuild` (`SVORebuild.cpp:254`) literally reads `int voxelsPerAxis = static_cast<int>(worldSize.x)` — **only the X component**, ignoring Y/Z — even though its own transform math two lines later (`:277-281`, `scale = worldSize/gridResolution` as a per-component divide, feeding a full matrix) is ALREADY non-uniform-scale-aware and would honor a non-cube `worldMax` correctly if `voxelsPerAxis` weren't collapsing it to `.x` first.

**Serialization already writes per-axis data that nothing currently uses for anisotropy.** `SerializeSdf` (`ShellOctreeGpu.h:830-831`) writes `gridMin`/`gridMax` per-component from the octree's own `worldMin`/`worldMax` — already correct, already per-axis — but `:829,832-835` hardcodes `localToWorld` to a UNIFORM `kWorldGridSize=10.0` scale, ignoring the per-axis extent it just wrote into `gridMin`/`gridMax`. This is a latent bug/simplification independent of this plan's own scope, but directly relevant: fixing it is part of what makes the box-tight approach work correctly.

**The chosen approach (embed-in-enclosing-cube, NOT true per-axis brick indexing):** keep the octree's own cube subdivision (`bpa = max(bpaX, bpaY, bpaZ)` — the smallest pow2-aligned cube that contains the body's true box-tight extent), but only BAKE the box-tight region within that cube, leaving bricks outside the body's true extent unallocated (`0xFFFFFFFF` in `brickGridLookup` — already the established "not allocated" sentinel per `_sdfBrickAllocated`'s existing handling, not a new mechanism). This means: **zero shader changes, zero GPU config-struct changes, zero parity-test rewrites** — `test_soa_sdf_serialize.cpp`'s `bpa³` lookup-table assertions stay green because the octree is STILL a cube grid; only the OCCUPANCY within it changes (most of a thin wall's cube now correctly has unallocated/empty bricks instead of baked/marched empty-space voxels). Traced through the survey's own analysis: the rejected alternative (true per-axis `bpaX/bpaY/bpaZ` brick indexing, rewriting the flat-index formula on CPU+GLSL in lockstep, touching the load-bearing 432-byte `OctreeConfig` layout) is more invasive AND still has to embed in an enclosing cube for ESVO descent anyway — it buys little over the embed-in-enclosing-cube approach unless that approach's own enclosing-cube waste (measured in BRICKS now, not voxels) proves too large in practice. Not attempting the per-axis-index approach in this plan; revisit only if M2's own measurement shows the brick-level waste is still unacceptable.

**Why this fixes BOTH problems from one change.** The oversized-cube-grazing-hit issue and the ~147× perf collapse share the SAME root cause (mostly-empty cube volume around thin bodies) — baking only the box-tight region means: (a) grazing rays no longer traverse large empty spans before hitting the surface (their `hitT`/`worldPos` shrink back to legitimate, tight values — closing the M3-round-5/6 "out-of-bounds" diagnostic finding), and (b) the GPU no longer pays brick-march cost for empty space, since those bricks are simply unallocated and the traversal's own existing `_sdfBrickAllocated` check already skips them cheaply (this mechanism already exists for sparse/lazy-residency scenes; this plan reuses it, doesn't invent it).

## Scope

1. **`BakeSdfWorld`**: add an optional box-tight bake-region parameter (a `glm::ivec3` or equivalent per-axis extent, defaulting to today's `(n,n,n)` cube so every existing caller is byte-unchanged) — the two bake passes (occupancy scan, SDF sample) iterate only within this tighter region instead of unconditionally `[0,n)³` on every axis. Bricks outside the region are never touched, so they stay in whatever "unallocated" state the octree builder already initializes them to.
2. **`BuildSdfBodyOctree`**: continue to build a cube octree (`bpa = max` of the enclosing cube needed to cover the body's TRUE bounding box, still pow2-rounded per the existing contract) — but the pow2-rounding must now be computed from the LARGEST axis of the body's true extent, not from a single caller-supplied `n` that's already assumed cube-sized. Verify the existing `2^floor(log2(n))` rounding-DOWN behavior doesn't silently under-cover a body's largest axis the way it did in the Cornell `kWallN=112` bug — this plan's own change is the right moment to make this contract explicit (round UP to the covering pow2, not down, unless the existing round-down behavior is confirmed intentional/safe for this use).
3. **`SVORebuild::rebuild`**: fix `voxelsPerAxis = worldSize.x` to derive from `max(worldSize.x, worldSize.y, worldSize.z)` (the enclosing-cube extent), so the already-correct per-component `scale = worldSize/gridResolution` transform math actually receives a meaningful non-cube `worldSize` instead of having it silently collapsed before reaching the matrix.
4. **`SerializeSdf`**: fix the hardcoded uniform `kWorldGridSize=10.0` `localToWorld` scale (`ShellOctreeGpu.h:829,832-835`) to honor the ALREADY-per-axis `gridMin`/`gridMax` it writes, rather than assuming uniform 10-unit coverage on every axis. This is a real, separate, pre-existing bug this plan's own investigation surfaced — fix it as part of this work since it's directly load-bearing for box-tight bodies to transform correctly, but call it out explicitly in the implementer's commit/report as its own distinct fix, not silently folded into the box-tight logic.
5. **Callers**: update the Cornell demo's wall/light/object bake calls (`BuildRenderGraph.cpp`, the M3-geom block) to pass each body's TRUE per-axis extent (walls are the primary beneficiary — currently baked into a 128³ cube for a ~2-unit-thick slab) instead of a cube `kWallN`. Every OTHER existing caller (tier-crossing spheres, DDGI leak-gate, `BodyOctreeSceneNode`'s own roughly-cubic recipe bodies, all test callers) should need ZERO changes — they already pass a cube-appropriate `n` for roughly-cubic bodies, and the new parameter defaults to preserving that exact behavior.

**Explicitly NOT in scope**: true per-axis brick-index rewriting (rejected approach, see Grounding above — revisit only if measurement shows it's needed); any change to the ESVO octree descent itself (still cube subdivision, unchanged); any change to the GPU `OctreeConfig` struct layout (zero new fields needed); any shader file changes (the existing `_sdfBrickAllocated`/unallocated-brick skip mechanism already handles this correctly once bricks outside the box-tight region are left unallocated); the DDGI shading-quality gap (dark objects, color bleed) that M3 round 6/7 flagged as a SEPARATE follow-up, likely-but-not-confirmed to improve once this lands (worth re-measuring after, not assumed).

## Gate

- **Correctness (regression, must be byte-identical or explicitly justified)**: every existing `BakeSdfWorld`/`BuildSdfBodyOctree`/`SVORebuild` caller that does NOT opt into a box-tight region must produce byte-identical output to today (the default parameter must be a true no-op for existing cube-body callers). `test_soa_sdf_serialize.cpp`'s parity assertions, `test_sdf_bake.cpp`, `test_baked_vs_virtual_parity.cpp`, `test_stored_sdf_march_mirror.cpp`, and every other test the survey identified as exercising this code path must pass unchanged.
- **The Cornell wall correctness gate**: after switching Cornell's wall bodies to a box-tight bake, the baked variant must still render a correct, coherent Cornell box (same bar M3 round 5 established — no regression on the already-fixed structural/color correctness), AND the M3-round-5/6 "out-of-bounds hit" diagnostic count must measurably shrink (ideally toward zero, or close to it) — this is directly, numerically checkable via the existing `[CornellDiag]` coarse-grid + full-buffer-OOB-scan instrumentation already left in place in `VulkanGraphApplication.cpp`, no new tooling needed.
- **The actual point of this plan — the performance gate**: re-run the SAME FrameTimer methodology M3 round 7 used (baked vs. virtual, same tick-150 capture path, same camera) and report the new baked FPS/frame-time plainly. The bar is NOT "match virtual's 126 FPS" (baked will always cost more than analytic tracing) — the bar is closing the ~147× gap to something in a genuinely real-time-comparable ballpark (a specific target number is NOT prescribed here; the M2 implementer/validator should report the actual achieved ratio honestly, whatever it is, per this whole program's standing "report the real number, don't just claim success" discipline).
- **Regression sweep beyond Cornell**: spot-check at least 1-2 other existing baked/stored-SDF demo scenes (the DDGI leak-gate scene is the survey's own named smoking-gun example — its `wallSdf` is ALSO a thin body in a cube, `kWallHalfExtent(1,15,15)` baked into `n=32`, per the survey's finding — this scene should ALSO benefit from this fix and is a natural second real-world validation case beyond synthetic tests).

## Self-Review

- **Why embed-in-enclosing-cube instead of true per-axis brick indexing?** The survey found this narrower approach reuses EXISTING per-axis AABB/transform machinery and the EXISTING unallocated-brick skip mechanism, needing zero shader changes and zero GPU config-struct changes — a much smaller, lower-risk change than rewriting the load-bearing 432-byte `OctreeConfig` layout and the CPU↔GLSL bit-parity-tested flat-index formula in lockstep. The true per-axis approach would STILL need to embed in an enclosing cube for ESVO descent anyway (the octree itself is fundamentally cube-subdivided), so it buys little for much more risk. Revisit only if M2's measurement shows the enclosing-cube's own remaining brick-level waste (not voxel-level, since voxels within an unallocated brick are never baked/marched at all) is still a problem.
- **Why fix `SerializeSdf`'s hardcoded uniform `kWorldGridSize=10.0` as part of this plan rather than filing it separately?** It's directly load-bearing for box-tight bodies — a wall's true per-axis extent won't transform correctly to world space if the matrix assumes uniform 10-unit coverage regardless of the box-tight region's actual shape. But it's being called out explicitly as its own distinct fix (not silently folded into "the box-tight logic") because it's a genuinely separate, pre-existing bug this investigation happened to surface, and future readers of the commit history should be able to tell the two apart.
- **Why is the Cornell wall's own bake call NOT in M1?** M1 needs to prove the core plumbing is a true no-op for every EXISTING caller before anything depends on the new box-tight path actually working correctly — Cornell's own validation (M2) should be testing a proven mechanism, not simultaneously debugging the mechanism and the first real caller of it.
- **Deliberate non-scope**: any shader change (none needed, per the survey); the ESVO descent's own cube-subdivision nature (fundamental, not something this plan touches); the ~432-byte `OctreeConfig` GPU struct layout (unchanged); the DDGI shading-quality gap (a separate, already-deferred follow-up — M3 checks on it honestly but doesn't attempt to fix it as part of this plan unless it turns out to be trivially downstream of this fix, in which case flag it back to the user for an explicit scope decision rather than silently expanding this plan).
- **Biggest risk**: the pow2-rounding direction question (round UP vs DOWN to cover a body's largest true axis) — the existing `BuildSdfBodyOctree` rounds DOWN, which already caused one real bug in this exact investigation (Cornell's `kWallN=112`→64 desync). M1's implementer must resolve this explicitly and test it with a deliberately non-pow2 body extent, not just the Cornell case (which will likely be hand-tuned to already be pow2-friendly) — the same "test the edge case deliberately, don't just rely on the common case happening to work" discipline Inc6's own non-integer-division fix required.
