# Node Self-Registration — Portable Fix Direction

## 1. Problem

`RenderGraph-System.md` §9.2-9.3 documents the existing node self-registration mechanism:
each node `.cpp` appends a registrar thunk to a global Meyers-singleton manifest via a
file-scope anonymous-namespace static initializer (`VIXEN_REGISTER_NODE`,
`NodeRegistration.h`), and because nothing else references that static, §9.3 requires
whole-archiving `RenderGraphNodes` to defeat the linker's normal dead-code stripping.
`test_node_self_registration.cpp` is documented as "the guard" — §9.3's own text says:
**"If that test goes red after a CMake change, check the link command for the whole-archive
flag first."**

**Root-caused 2026-07-12** (during an unrelated ctest-sweep audit): the guard went red on
this branch under MSVC — `NodeSelfRegistration.RegistersAllBuiltInNodes`/
`ReplaysIntoEachRegistryInstance` both report `GetNodeTypeCount() == 0` instead of the
expected ≥32 — **with the whole-archive flag present and correct**. §9.3's own advice
("check for the missing flag") does not find this bug, because the flag isn't missing; it's
present but insufficient for this link topology. Two research passes (this session,
2026-07-12) established why:

1. Since [[Graph-Derived-Node-Linkage-Inc1-Plan-2026-07]] (§9.7, M2), each node `.cpp` also
   compiles into its own `RenderGraphNode_<Name>` **OBJECT library**, and `RenderGraphNodes`
   (the STATIC facade) links all of them `PUBLIC`.
2. CMake propagates a STATIC library's linked OBJECT-library members onto the **final link
   line as loose `.obj` files**, not embedded inside the STATIC archive itself. Confirmed by
   direct inspection: `RenderGraphNode_CameraNode.obj` lives in its own
   `RenderGraphNode_CameraNode.dir/`, never inside `RenderGraphNodes.lib`.
3. `/WHOLEARCHIVE` (MSVC) and `$<LINK_LIBRARY:WHOLE_ARCHIVE,...>` (CMake ≥3.24) only solve
   **archive-member selection** — the problem of an object inside a `.lib` only being pulled
   in if something already-included references one of its symbols. They do not apply to
   OBJECT library targets at all (CMake docs: the `WHOLE_ARCHIVE` feature of
   `LINK_LIBRARY` is explicitly a no-op for OBJECT/INTERFACE targets — "any CMake target of
   type OBJECT or INTERFACE will ignore the feature aspect of the expression and instead be
   linked in the standard way"), and MSVC's `/WHOLEARCHIVE:<library>` is documented as taking
   "a pathname to a static library," not a loose `.obj`.
4. The actual mechanism stripping the registrars is a **different** one: MSVC's `/OPT:REF`
   (linker COMDAT/section garbage collection, on by default in this project's build config)
   discards individually-unreferenced COMDATs/sections regardless of whether the containing
   object file arrived on the link line as a loose `.obj` or as an archive member. Whole-
   archiving `RenderGraphNodes` correctly ensures every per-node `.obj` is *present* on the
   link line; it does nothing to stop `/OPT:REF` from then discarding the specific
   unreferenced static-initializer COMDAT inside each of those `.obj`s.

Two follow-up fix attempts were tried and ruled out this session (kept here so they are not
re-attempted without re-deriving why they fail):

- **`/INCLUDE:<mangled_symbol>` per registrar, generated by CMake.** Requires knowing each
  registrar's MSVC-decorated name. The registrar is currently declared inside an anonymous
  namespace, whose mangled form embeds a compiler-internal, per-TU hash component
  (`?A0x<hash>`) that is not predictable at CMake-configure time and is not guaranteed
  stable across incremental rebuilds or compiler versions. Not viable without first removing
  the anonymous namespace (see §3 below).
- **Same-TU `#pragma comment(linker, "/include:...")` self-reference trick** (a real,
  documented MSVC idiom — see Ofek Shilon, "Forcing Construction of Global Objects in Static
  Libraries," and used by Boost/ATL for exactly this class of problem). Requires
  `extern "C"` linkage for a CMake/preprocessor-computable decorated name (x64 has no
  decoration at all for `extern "C"`; x86 gets a leading `_`). **Ruled out for this
  topology specifically**: the trick only works if the object file containing the pragma is
  fed directly to the final link step. VIXEN's registrar TUs go through an intermediate
  STATIC archive (`RenderGraphNodes`) before reaching any executable/DLL; archive-member
  extraction happens *before* `/include:` directives are even processed by the linker, so
  the pragma cannot rescue a member sitting inert inside a `.lib` that nothing else already
  pulled in. (It would work if VIXEN's node registrars linked straight into the final
  binary with no intermediate static lib — they don't.)

## 2. Why this matters beyond one test

This is not merely a test-infra nuisance. The stripping risk is a property of the
**mechanism** (anonymous-namespace static-init side effect + no consuming symbol reference),
not of any one linker's current default flags. It happens to be latent/inert on the
GCC/WSL side today (that toolchain's default GC behavior tolerates it, per §9.3's original
"verified empirically" note — itself now understood to be toolchain-specific, not a
mechanism guarantee) and newly triggered on MSVC by the Inc-1 OBJECT-library split
surfacing the COMDAT-GC gap. A future MSVC update, a `/OPT:REF`-equivalent default change on
another toolchain, LTO, or an `/OPT:ICF` interaction could resurface the same failure mode
anywhere this pattern is used — and it is used, unmodified, by every one of VIXEN's ~53 node
types (`RenderGraph-System.md` §9.2, §9.4).

`VixenApp`'s own real linkage is unaffected today — [[Graph-Derived-Node-Linkage-Inc1-Plan-2026-07]]'s
M4/Bug 3 already forces whole-archiving all of `VixenApp` itself for its real consumers, which
happens to keep those specific node `.obj`s' COMDATs alive as a side effect of pulling in
everything else `VixenApp` needs. The bug is currently confined to the **unscoped test
facade** (`libraries/RenderGraph/tests/*` links the full `RenderGraphNodes`/`RenderGraph`
facade by design, per that same plan's §"M4"), which is precisely the guard §9.3 relies on to
catch registration breakage — so today the guard itself is broken on MSVC, silently. This
should be fixed at the mechanism level, not patched by further linker-flag layering that has
already proven fragile twice.

## 3. Direction: intrusive self-registering linked list

Replace the `std::vector<std::function<void(NodeTypeRegistry&)>>` + anonymous-namespace
`const bool` static-init pattern with a classic **intrusive self-registering linked list** —
each node's registrar becomes a small static object whose *constructor running* (not "was my
symbol referenced by something else") is what links it into a global list. This is
structurally immune to archive-member-selection stripping AND to COMDAT/section garbage
collection on every toolchain, because there is no "unreferenced symbol" for a GC pass to
find: the registrar object's constructor is inherently reachable the moment its enclosing
`.obj` is linked in at all (which whole-archiving `RenderGraphNodes` already guarantees —
§9.3's existing whole-archive requirement stays, it is the archive-member-selection half of
the problem and is still correct and necessary; only the COMDAT-GC half needs a mechanism
change, not the archive step).

### 3.1 Shape (illustrative, not final — the implementer verifies against the real header)

```cpp
// NodeRegistration.h
namespace Vixen::RenderGraph::detail {

struct NodeRegistrarLink {
    void (*registerFn)(NodeTypeRegistry&);
    NodeRegistrarLink* next;

    // Constructor is the whole mechanism: running it (guaranteed the moment this
    // object's enclosing .obj is linked in — no symbol reference required) links
    // this node into the global list via the Meyers-singleton head accessor.
    explicit NodeRegistrarLink(void (*fn)(NodeTypeRegistry&));
};

// Meyers singleton — same pattern already used for NodeRegistrars() today, so no new
// static-initialization-order risk is introduced (RenderGraph-System.md's existing
// discipline extends one level down, it is not a new technique for this codebase).
NodeRegistrarLink*& HeadLink();

} // namespace detail

#define VIXEN_REGISTER_NODE(NodeTypeClass)                                       \
    namespace {                                                                  \
        void VIXEN_REGISTER_NODE_CONCAT(vixen_register_fn_, __COUNTER__)(        \
            ::Vixen::RenderGraph::NodeTypeRegistry& reg) {                       \
            reg.Register<NodeTypeClass>();                                       \
        }                                                                        \
        ::Vixen::RenderGraph::detail::NodeRegistrarLink                          \
            VIXEN_REGISTER_NODE_CONCAT(s_vixen_node_registrar_, __COUNTER__)(    \
                &VIXEN_REGISTER_NODE_CONCAT(vixen_register_fn_, __COUNTER__));   \
    }
```

`RegisterAllNodes(registry)` walks `HeadLink()`'s chain instead of iterating a
`std::vector`; the public signature and observable behavior (§9.2's "replay into any
registry" contract, tested by `ReplaysIntoEachRegistryInstance`) are unchanged.

### 3.2 Why this mitigates the specific risks raised during scoping (recorded so the
implementer does not have to re-derive the reasoning)

- **Blast radius on the live app.** `RegisterAllNodes(NodeTypeRegistry&)` keeps its exact
  signature and contract; every call site (app, editor, benchmark, tests) is unaffected.
  Land as a pure internal-mechanism refactor, verified byte-for-byte-equivalent to today's
  registry contents on the GCC/WSL path (already working) *before* it needs to also fix the
  MSVC path — proves the mechanism sound independent of the stripping fix.
- **Static-init-order fiasco.** Mitigated by reusing the Meyers-singleton accessor pattern
  (`HeadLink()`) this codebase already trusts for `NodeRegistrars()` today — each node's
  constructor only ever touches the list via the function-local-static accessor, never a
  raw global, so construction order across the ~53 node TUs is irrelevant (the standard's
  first-use guarantee handles it, same as today).
- **Re-verification against real app behavior.** `test_node_self_registration.cpp`'s
  existing type-keyed `Has<CameraNodeType>()`-style checks already exercise real
  instantiation through the new path, not just a headcount. Increment plan (§4 below) adds
  a real windowed live-gate run of `VIXEN.exe` per this project's "live-run gate is
  authoritative for GPU/app work" discipline (do not trust a passing unit test alone for a
  change to core node-discovery machinery) before calling this done.

## 4. Non-goals / explicit relationship to Graph-Derived Node Linkage

This direction is **not** a re-litigation of [[Graph-Derived-Node-Linkage-Direction-2026-07]]
or its shipped Inc-1. That epic controls **which node types a given app binary links at all**
(build-size scoping, `VixenApp`-specific, via a generated per-app manifest). This direction
controls whether **the registration mechanism itself reliably survives any correct linker
configuration**, for whichever nodes a given consumer (test binary, app, or a future scoped
binary) does link. The two are orthogonal and compose: Inc-1's OBJECT-library split is in
fact what surfaced this bug (by moving node object code out of a plain STATIC archive into a
structure where COMDAT GC could reach it independent of archive selection) — fixing the
registration mechanism here does not undo or change any of Inc-1's link-scoping behavior,
and Inc-1's scoped-linkage path is not itself broken today (§2 above) — only the unscoped
test facade currently exercises the broken mechanism.

Also **not in scope**: changing `RenderGraph-System.md` §9.3's whole-archive requirement for
`RenderGraphNodes` itself — that requirement (archive-member selection) remains necessary
and correct; this direction adds a second, independent fix for the COMDAT-GC half of the
problem that whole-archiving was never able to address. §9.3's own advice text ("check the
link command for the whole-archive flag first") should be corrected as part of this work's
documentation update (§5) — it currently misdirects a future debugger toward the flag that
was never the problem.
