# View Contract Inc-5 — Undertow Migration Plan (2026-07-12)

**Program:** `Renderer-Agnostic-View-Contract-Design-2026-07.md` §6.5 (the undertow system this program
subsumes), §3 (four faces). **Prior:** Inc-1 (data emitter) + Inc-2/2b (renderer-agnostic `IView` host +
reflection blob/generic marshaler) + Inc-3 (C# data-upload face, AoS wire, round-trip proven) — **ALL DONE
and merged to both origins** (VIXEN main, Yeroket main). Inc-3's own doc named this deferred slice
"Inc-5+" explicitly (D1: "the undertow migration... is Inc-5+").

## Goal

Migrate undertow's hand-rolled `Undertow.Authoring.Codegen`/`ViewSchema.cs` view-contract codegen onto the
shared Yeroket kernel-framework `[View]` schema + emitter family, so undertow becomes a **consumer** of the
content format instead of its **author** — reversing the current, documented-as-temporary inversion (see
Ground Truth below) and completing `[[vixen-owns-content-format-not-consumer]]` for the one remaining
system that still violates it.

but DO re-verify file:line if code has moved)

## Scope boundary (what Inc-5 IS and is NOT)

- **IS:** (a) SoA wire-format emit support in the Yeroket kernel-framework's existing `ViewLayout`/
  `ViewWriterEmitter` machinery (Inc-3's `Soa` case, currently a deliberate throw, becomes real); (b) a
  SoA-aware C++ reader counterpart (extending or sibling to Inc-3's `ViewWireReader`/`ViewStore` path);
  (c) declaring undertow's 5 view sections (`Bodies`/`Hud`/`HudFactions`/`HudEvents`/`HudInspect`) as
  `[View]`/`[ViewSection(Layout=Soa)]` schemas — reusing Inc-Ovr's newly-shipped `[Projected]`/
  `[Overridden]` attributes wherever a column's `Source` expression (e.g. `HudFactionFocused`'s
  `el.IsFocused ? (byte)1 : (byte)0`) is a transform rather than an identity bind; (d) regenerating
  `view_contract.h` (VIXEN C++ side, replacing `EmitViewContractHeader.cs`'s hand-rolled emitter output)
  and a generated C# writer (replacing `ViewWriterGenerator.cs`/`EmitViewWriter.cs`'s hand-rolled output),
  both stamped with the Inc-3 `ViewVersionHash` (D4: "replacing undertow's hand-bumped `FormatVersion`");
  (e) preserving the exact `UTVW`/`UTFB` wire bytes undertow's real host/renderer already read/write today
  (a byte-for-byte compatible regeneration, not a new wire format) — this is a REPLACEMENT of the
  generator, not a change to what gets sent over the seam; (f) retiring `Undertow.Authoring.Codegen`'s
  view-specific emitters (`EmitViewContractHeader.cs`, `EmitViewWriter.cs`/`ViewWriterGenerator.cs`) and
  `ViewSchema.cs`'s hand-declared `FormatVersion`/intro-version constants once the schema-driven
  regeneration is proven byte-identical.
- **PROOF vehicle:** the same discipline every prior increment in this program (and the View-Model-Binding
  program) has used — re-derive an ALREADY-SHIPPED, ALREADY-TESTED behavior through the new mechanism and
  prove byte/behavior-identical output, THEN delete the hand-written duplicate. Concretely: declare
  undertow's real `Bodies`/`Hud`/`HudFactions`/`HudEvents`/`HudInspect` schema through `[View]`/
  `[ViewSection(Layout=Soa)]`, regenerate `view_contract.h` + the C# writer, and diff the regenerated
  bytes against what undertow's CURRENT hand-rolled generator produces for a real captured frame (or the
  existing golden tests' fixtures, per `ViewContractHeaderTests.cs`/`SchemaJsonEmitTests.cs`) — exact
  match required before touching anything undertow-side. Only after that match is proven does this plan
  retire the old emitters and switch undertow's actual `.csproj` `Analyzer` reference from
  `Undertow.Authoring.Codegen`'s view slice to the Yeroket kernel-framework CLI's generated output.
- **IS NOT:** migrating undertow's OTHER ~30 codegen emitter files (save codecs, patch parsers, authored-
  kind builders, effect/action/param/system registration, merge logic) — those are a separate, much
  larger, explicitly out-of-scope epic; this plan touches ONLY the view-contract slice named above.
- **IS NOT:** changing the wire bytes/protocol undertow's host (`vixen/app`) and renderer (`vixen/render`)
  actually exchange today — this is a generator-replacement, not a protocol redesign. If the regenerated
  output is NOT byte-identical to what's shipping today, that is a BLOCKER to investigate and resolve
  (likely a schema-declaration mistake on this plan's part), not something to silently accept as "close
  enough" or paper over by bumping the version.
- **IS NOT:** touching anything in undertow's `core/` Env-1-authoritative sim types — all generated/
  consuming code for this migration lands in `Undertow.View`/`Undertow.Bridge` (the existing ENV-2-
  permitted area), per the hard wall documented in `docs/master-roadmap.md:20`.
- **IS NOT:** the dispatch-side kernel migration hinted at by `TagDensityKernel.cs`'s comment (a future
  `[VMKernel]`/Burst-dispatch integration) — that is a different, unstarted, much larger epic (compute
  dispatch, not view-contract codegen) and is explicitly not this plan's concern.
- **Reuse, don't reinvent:** Inc-3's `ViewLayout` core, `ViewWriterEmitter`, `ViewVersionHash`, and the
  `[View]`/`[ViewSection]` attribute family (all shipped, Opus-validated, on both origins) are the
  substrate this plan extends (SoA emit) and finally applies to a real external consumer (undertow) for
  the first time. Inc-Ovr's `[Projected]`/`[Overridden]` attributes (also shipped, this session) are the
  mechanism for any `ViewSchema.cs` column whose `Source` expression isn't a flat 1:1 bind (e.g. ternaries,
  casts, computed values — several columns in the real schema have exactly this shape).

### Task 4 — Declare undertow's real schema + regenerate + prove DECODED-VALUE identical (RESCOPED 2026-07-12, TWICE)

**Rescoped after a real architectural gap was found during Milestone 3 (see Progress Log entry below):**
undertow's live `vixen/app/src/main.cpp` consumes a TYPED, per-section C++ accessor class
(`undertow::view::BodiesSection` with `position()`/`orbit_points()`/etc. methods, generated from
`view_contract.h`) — but the shipped Yeroket `[View]` pipeline (Inc-1/2/2b + this program's own Inc-5
Milestone 2) only emits a GENERIC reflection blob (`ViewBlob`/`ViewFieldDesc`, consumed by name/index at
runtime via `BlobView`/`ViewStore`) — architecturally a different consumption model, not a drop-in
replacement for `view_contract.h`'s typed-accessor shape. There is no emitter anywhere in Yeroket that
produces a `view_contract.h`-shaped file. Task 4 was first rescoped to prove WIRE-BYTE identity only, but a
SECOND rescope was needed after discovering undertow's real `UTVW` wire (magic + per-section TOC +
per-column TOC + 16-byte alignment, byte-offset column lookup — `ViewBufferBuilder.cs`) is a
STRUCTURALLY DIFFERENT binary protocol from Yeroket's generated `UTVA`/SoA wire (no TOC, no alignment,
flat declared-field-order stream — `ViewWireFormat.cs`). These are two independently-designed wire
formats (different magic bytes even) — a byte-diff between them can never match regardless of schema
correctness, so "wire-byte identical" was never an achievable bar either. **Task 4 is therefore rescoped a
second time to prove DECODED-VALUE identity**: decode undertow's real `UTVW` bytes via undertow's own
reader/accessor logic, decode the schema-driven `UTVA`/SoA bytes via `ViewWireReaderSoa` (Milestone 2), and
assert the SAME logical values come out for the SAME reference frame (same body count, positions, faction
names, etc.) — this is the achievable, meaningful realization of "prove a real already-shipped behavior is
reproduced through the new mechanism," mirroring Milestone 2's own round-trip proof discipline, just
cross-validated against undertow's real writer's decoded output instead of a hand-built expected buffer.
NOT wire-byte identity, NOT `view_contract.h` TEXT identity — see Follow-ups for both deferred gaps.
- Declare the 5 real sections (`Bodies`/`Hud`/`HudFactions`/`HudEvents`/`HudInspect`) as `[View]`/
  `[ViewSection(Layout=Soa)]` schemas. **Gap #2 (found + resolved before writing schemas):** `[Projected]`
  is consumed ONLY by `RmlDataModelEmitter.cs` (the RmlUi/View-Model-Binding C++ face) — `ViewWireFormat`'s
  `ToBuffer()` generator never reads `f.Projection`, so declaring `[Projected]` fields would compile but
  NOT transform anything in the writer path. **Resolution (confirmed by controller):** do the transform in
  hand-written adapter code (SimFrame → the generated `<Name>ViewWriter`'s already-transformed fields),
  matching the existing `Hud.cs`/`EditorLayers.cs` precedent of plain pre-transformed struct fields;
  `[Projected]` stays attached to the 3 name-mismatch/transform fields as documentation/traceability only
  for this proof, not a functioning mechanism — inventing new C#-side callable-dispatch emitter machinery
  is explicitly out of scope for this milestone (Follow-ups).
- Regenerate the C# writer output via the SoA mechanism (Milestone 2), and prove DECODED VALUES read back
  (via `ViewWireReaderSoa` on the schema-driven side, undertow's own reader on the real side) match for the
  SAME logical reference frame (extend/capture a frame that exercises populated Str/ListVec3f columns, per
  the proof-fixture gap both prior milestones' validators flagged) — this is the mandatory, non-negotiable
  gate before Task 5. Do NOT attempt to regenerate or diff `view_contract.h` itself this task, and do NOT
  attempt a raw wire-byte diff — both are out of scope/unachievable as established above.

### Task 5 — Retire the hand-rolled undertow WRITER generator only (RESCOPED 2026-07-12 — see Task 4)

- ONLY after Task 4's decoded-value-identical proof: switch the WRITER half of `Undertow.View.csproj`'s

  `ViewWriterGenerator.cs`/`EmitViewWriter.cs` to the Yeroket kernel-framework CLI's generated writer

## Gates / guardrails

- Byte-identical regeneration (Task 4) is mandatory and non-negotiable before Task 5 begins — do not
  proceed to retiring the hand-rolled generator on a "close enough" or "the tests still pass" basis if the
  raw bytes differ even by one byte in a way that isn't explained and justified.
- Every `Source` expression's semantics must be preserved EXACTLY through its `[Projected]` transplant —
  this program's own precedent (View-Model-Binding Inc-Ovr) shows a byte-identical bit-logic re-derivation
  is achievable and is the bar to meet, not "approximately the same."
- No generated/consuming code for this migration may land in undertow's `core/` Env-1-authoritative sim
  types — confirm every new file's project membership respects the existing Env-1/Env-2 hard wall.
- The SoA serializer must correctly handle `Str`/`ListVec3f`'s variable-length offsets+blob encoding
  (`ViewSchema.cs`'s own doc comment) — this is a real complexity, not a flat fixed-stride array; do not
  under-scope Task 2/3 by treating all columns as fixed-size.
- Cross-repo work (Yeroket + VIXEN + undertow — THREE repos this time, not two) needs its own
  worktree-pairing discipline; follow the established convention from prior cross-repo increments
  (config-struct-codegen epic, kernel-unification program, View-Model-Binding Inc-Ovr) rather than
  improvising a new one.
- rtk masks git exit codes — use `/usr/bin/git`, `sha256sum`, `cmp` for evidence in ALL THREE repos. Poll
  long builds actively, never overlap builds of one target.
- Commit in worktrees (pre-blessed per convention). Do NOT push without explicit confirmation all three
  repos' halves are ready to land together (a partial cross-repo push here is worse than usual — undertow's
  `.csproj` change coupling means an incomplete push could leave undertow's build broken against a Yeroket
  main that doesn't yet have the SoA emitter).

  `Bodies.OrbitPath` (`ListVec3f` — a nullable, per-row VARIABLE-LENGTH list of points, a 2-level nesting
  with no representation at all) are consequently NOT declarable — Milestone 3's `UndertowBodies` schema
  proves only the other 7 columns. A future increment would need to teach `ViewModel`/`ViewWireFormat`
  (both AoS and SoA paths) a new Vec3f-scalar field kind (fixed 12-byte triple) and a new variable-length
  struct-list field kind (reusing the existing offsets+blob machinery, generalized beyond String columns)
  before `Bodies` can be declared in full — real, undesigned mechanism work, not a workaround
  (flattening Vec3f to 3 separate floats was considered and rejected: it doesn't generalize to
  `OrbitPath`, since row count and per-row list length are different cardinalities).
- **A C#-side `[Projected]`-dispatch extension to `ViewWireFormat`/`ViewWriterEmitter`** (gap #2, discovered
  during Milestone 3, 2026-07-12): today `[Projected]` only affects the RmlUi `RmlDataModelEmitter.cs` C++
  face; the View Contract C# writer (`ViewWireFormat.EmitScalar`) never dispatches to a callable. If a
  future schema genuinely needs the writer itself to invoke a transform (rather than pre-transforming in a
  hand adapter, as Milestone 3 does), this would mean emitting a call to a C#-side
  `Vixen.Views.Generated.<Method>(access)` before serializing — new, undesigned emitter work, deliberately
  not built under Milestone 3's time pressure.
- **Unifying (or bridging) undertow's real `UTVW` wire protocol and Yeroket's generated `UTVA`/SoA wire
  protocol** (gap #3, discovered during Milestone 3, 2026-07-12): the two are structurally different binary
  formats (TOC+16-byte-alignment+ID-lookup vs flat declared-order stream) — Milestone 3 worked around this
  by proving DECODED-VALUE identity instead of wire-byte identity, but a real writer-generator retirement
  (Task 5) means undertow's C++ reader side must eventually also move off `view_contract.h`'s `UTVW`-TOC
  reader onto `ViewWireReaderSoa`'s `UTVA`/SoA reader (or Yeroket's emitter must learn to speak `UTVW`'s
  exact wire dialect) — neither is designed yet; Task 5's own implementer must scope this explicitly rather
  than assuming "switch the Analyzer reference" is a small mechanical step.
- **A typed C++ accessor header emitter from `ViewBlob`** (discovered as a genuine gap during Milestone 3,
  2026-07-12): Yeroket's shipped `[View]` pipeline has no emitter producing a `view_contract.h`-equivalent
  file (named per-section accessor classes with cached column pointers and typed methods like
  `position(i)`/`orbit_points(i)`) — only the generic reflection-blob consumption model
  (`ViewBlob`/`BlobView`/`ViewStore`) exists. Retiring `EmitViewContractHeader.cs` (and therefore fully
  completing "undertow becomes a pure consumer") requires EITHER building this new emitter face as its own
  scoped increment, OR a separate, larger decision to migrate undertow's C++ call sites (`main.cpp` and
  similar) to consume the generic `BlobView`/`ViewStore` API directly instead of a generated typed header
  — the two are genuinely different amounts of work and neither was designed under this decision's time
  pressure; scope and decide between them as a dedicated increment before attempting it.
- **`ViewWireReader`/`ViewWireReaderSoa` `Cursor` duplication** (flagged by Milestone 2's Opus validator):
  the two C++ readers duplicate their bounds-checked `Cursor` struct (magic check, version guard,
  trailing-byte check) verbatim. Sound today; fold back into one shared cursor once `ViewFieldDesc` gains
  a real per-field layout flag (likely a natural side effect of Milestone 4's schema work).
- Migrating undertow's OTHER ~30 `Undertow.Authoring.Codegen` emitter files (save codecs, patch parsers,
  authored-kind builders, effect/action/param/system registration, merge logic) — a separate, larger epic;
  this plan touches only the view-contract slice.
- The `TagDensityKernel.cs`-hinted future `[VMKernel]`/Burst-dispatch integration — a different epic
  (compute dispatch), not view-contract codegen.
- View Contract program's remaining faces per the parent design doc: face 2 (authoring reference), face 4
  (view→action, the AppFlow convergence, parent §7) — unrelated to this plan's undertow-migration scope.
- View-Model-Binding Inc-E (authoring tooling / UX API + lint guards) — a sibling program's own remaining
  item, unrelated to this plan.

## Note

This is the first increment in the View Contract Codegen program that actually touches the undertow repo
— every prior increment (Inc-1 through Inc-3) was deliberately scoped to prove the mechanism in-tree
first, per each increment's own "do NOT touch undertow" discipline (D1 in multiple designs). That
discipline paid off: the SoA gap this plan must close was identified and explicitly deferred, not
discovered as a surprise now. Per the program's own established pattern (and View-Model-Binding's, most
recently with Inc-Ovr): the proof is not "the new schema compiles" — it is "a real, already-shipped wire
format is reproduced byte-identically through the new mechanism, and the old hand-rolled generator is
retired, not left running alongside it."
