- Audited VIXEN `d3316e7d`, read-only KFR `fbad96d`, and Undertow `00abd7d`'s current register.

## 3. Category findings

### A. Generic infrastructure that should remain fixed

The reusable engine boundary is substantial and is already in the right layer: RenderGraph dispatch, resource providers, hazards/barriers, queue scheduling, body-instance iteration, ESVO node/brick addressing, stack/restart and tier crossing, residency, mip pools, uploads, visibility requests, reservoir storage, and global GI accumulation. The current body pass reads concatenated scene pools indexed through per-instance octree configuration (`Recipe-Container-Format-Contract-2026-06.md:213-229`). Keep those mechanisms shared when recipe or volume policy is extracted.

Some global rendering algorithms are also fixed renderer work rather than per-recipe behavior: ReSTIR reservoir mechanics, DDGI atlas reduction/hysteresis, photon-cell cache management, exposure measurement/tonemapping, and occlusion/candidate prepasses. They may have user-visible effects, but their state and schedule are shared across the frame. A recipe-specific decision should enter them through values and declared response functions, not fork the queue, barrier, or cache machinery.

Two A artifacts contain mixed behavior that deserves follow-up when seams are introduced:

- `SceneBindings.glsl` combines common bindings with most of the stored-SDF and composed-voxel traversal implementation. Its LOD thresholds, mip choices, fixed steps, and any-hit branches are candidates for an injected policy, even though the file's dominant job is shared scene infrastructure.
- `TraceWorld.glsl` is the right common call boundary, but its `isCloserHit` tie rule was introduced to stabilize adjacent Cornell surfaces, and it takes procedural emission from `recipeParams[3]` (`TraceWorld.glsl:29-40,64-87`). These should be isolated as fixture/data policy while preserving stable generic hit selection.

### B. Recipe/material behavior baked into shaders

Current surface response is still narrow and partly duplicated across shading paths. `Brdf.glsl` has a fixed dielectric Fresnel value and documents the missing metalness input (`Brdf.glsl:8-11`); `VoxelChannelFormat.glsl` defines metallic and density IDs, but `StoredSdf.glsl`'s hit-channel sampler reads color, roughness, and emission (`StoredSdf.glsl:356-378`). `Materials.glsl` maps material IDs to scene palettes rather than consuming a content identity. The renderer-side material gap investigation also found that simulation material identity does not yet flow through `render_recipe`/view data to a render response table (`~/scripts/orchestra/reports/material-render-gap-2026-09-29.md:12-23`).

The optional bucketed path is more advanced than an unimplemented design sketch. The graph has opt-in recipe-bucket nodes and `MultiDispatchNode` wiring (`BuildRenderGraph.cpp:1013-1128`). `VulkanGraphApplication.cpp:918-977,1179-1190` builds recipe-specialized pipelines, including an optional specialized shade path. Its emitted material code still assigns instance color, `roughness = 0.5`, and `recipeParams[3]` emission (`libraries/SVO/include/Recipe/SpecializedRecipeShaderGlsl.h:346-408`). It proves that recipe-aware dispatch can exist without changing generic scheduling, but its response contract is still hand-coded.

`ProbeGather.comp` uses a Lambert diffuse term, `SpatialReuseShade.comp` and `HitAccumCellShade.comp` use the common BRDF, and emission is represented differently in record padding or a recipe parameter. These paths need one declared source of material/channel meaning if they are to stay consistent. `ProbeApply.comp` is classified A: it reduces already-computed radiance and updates the shared DDGI atlas; it does not choose a recipe's surface response.

### C. Per-volume/per-region traversal adjustments

There is no general volume-policy callback or user-authored cutaway/fog/density integration evident in the audited shader set. The fixed controls are dispersed among `BodyFootprintRegime.glsl`, `MipFallback.glsl`, `StoredSdf.glsl`, and the much larger `SceneBindings.glsl`. A `SEM_DENSITY` / `FK_DENSITY` label exists (`VoxelChannelFormat.glsl:9-12`), but a semantic ID by itself does not implement extinction, participating media, or an arbitrary traversal override. The stored-SDF branch is a signed-distance surface marcher with fixed limits and epsilon (`StoredSdf.glsl:900-920`), not a pluggable density volume.

Candidate per-body/per-region policy data could include bounds or region identity, density/extinction fields, step/epsilon adjustment, footprint/LOD bias, and a cutaway predicate. The fixed traversal caller would also need to pass ray origin/direction and current interval/cell scale, provider kind, channel view, and any resolved policy outputs. Which values may affect exact simulation state remains an authority question: the renderer should only consume a view/mirror result.

### D. Game-specific logic in the renderer

`Materials.glsl` is the clearest leakage: explicit Cornell/tunnel/city material ID palettes (`Materials.glsl:7-10,18-45`). Cornell seam tie-breaking and `recipeParams[3]` emission are smaller embedded leaks in shared traversal/shading files. They should become fixture data or recipe/material declarations. The general principle is already ruled: VIXEN is a module the game uses, not a container for the game (`undertow/docs/in-progress.md:17475-17499`, R106).

The audited KFR tree is consistent with that direction: it describes itself as a library consuming one loader-owned session, and its current app builds a generic UI graph from contract documents (`KernelFederationRenderer/README.md:3-14`, `app/src/session_renderer.cpp:26-55`). No tracked KFR GPU shader source or game-specific GPU job was found.

### E. Debug, test, dormant, or dead

The shader inventory includes isolated RenderGraph autosync/fan-in demos, an instancing demo, the standalone probe smoke shader, `ComputeTest`, an unwired sky-sphere scaffold, old VoxelRayMarch and backup files, and an RT voxel shader family with no active pipeline node in the application. Keep these out of the production facade contract. Where a test fixture still exercises a desired material, represent it as authored fixture data rather than retaining game palettes in shared shaders.

## 4. Plug-in seam options (for owner decision)

### Seam positions and data

- **Recipe/material seam:** after a traversal returns a `WorldHit`/`HitRecord`, before direct lighting, DDGI ray contribution, or hit-cell shading consumes color, roughness, normal, and emission. Existing context includes `recipeId`, `providerKind`, `recipeParams[6]`, instance color, `HitRecord`, and per-octree `channels[]` / `channelCount`. Missing today is a shared authored identity/contract that says which material response and channel subset a recipe supplies.
- **Volume/region seam:** inside the stored-SDF/composed traversal before a cell march or LOD/mip fallback decision. Existing context includes ray state, current instance/octree configuration, cell/brick address, channel layout, residency, and ray footprint. A volume policy would need to return a bounded decision/data view (for example density/extinction, step constraint, footprint bias, or cutaway result) without taking ownership of stack, node/brick fetch, restart, residency, or scheduling.
- R309's GPU-layout rule gives a useful constraint: generate GPU structs from the fields GPU-domain kernel systems actually bind, rather than declaring another kind-level layout flag (`undertow/docs/in-progress.md:26680-26687`). It does not decide the material vocabulary or which system owns volume policy.

### Options

| Option | Shape | Trade-offs |
|---|---|---|
| **1. Specialization constants plus compact parameters** | The fixed pass calls a small known set of policy functions. Per-recipe or per-volume parameters choose values/branches at pipeline or dispatch setup. | Small change to current pass split and low runtime indirection. The behavior vocabulary stays bounded; complex behavior expands variants or grows fixed shader branches. Specialization may increase pipeline variants/cache management. |
| **2. Facade-emitted recipe shader variants** | GPU-domain declarations emit the response/layout and optional volume policy; compile a per-recipe or per-policy shader and dispatch through the existing bucket/`MultiDispatchNode` path. | Builds on implemented bucketing and generated per-recipe pipeline code, and can remove unused response/channel work. It requires facade validation, codegen rules, stable cache keys, and a way to bound hot variants. This is the closest fit to the current optional specialized shade prototype. RT callable shaders could be evaluated as a later implementation of this option only if the RT pipeline becomes an active supported route; the current RT shader family is dormant. |
| **3. Data-driven uber-shader records** | Keep one/few compiled traversal/shading shaders; bind generated material and volume-policy tables keyed by recipe/material/region. Read parameters and channel descriptors at runtime. | Avoids shader-per-recipe growth and supports live data changes. It adds indirection and divergent branches, and contracts need to describe record bounds, fallback behavior, and valid field combinations. |

These are alternatives for owner review, not decisions. All retain fixed traversal and resource ownership, and let declared behavior plug into a stable call site.

## 6. Proposed sequence

1. **Keep the A boundary stable and remove obvious D leakage.** Preserve shared stack/restart, residency, pools, upload, resource scheduling, barriers, and dispatch. Move the ID palette and Cornell test decisions into fixture/material data. Treat `TraceWorld` as shared hit traversal; avoid changing its stable generic behavior while separating those fixture inputs.
2. **First vertical slice: recipe material response for the tug and asteroid.** Use the existing hit-record and optional bucketed-shade path. Declare the response fields and output semantics used by those recipes (at minimum color/albedo, roughness, metalness, emission, with normal semantics if needed); generate/bind the GPU layout from actual shader use under R309. Replace `inst.color`, fixed `0.5` roughness, and `recipeParams[3]` emission in the specialized shade. Route the same response through direct lighting, probe contributions, and cell shade so the visible result and GI agree. Keep traversal unchanged in this slice. The precise tug/asteroid recipe and material identities need owner confirmation; the renderer source census does not identify those game content rows (inferred).
3. **Second vertical slice: mining cut volumes.** First consume the authoritative result of the R294 C9 voxel-world edit and expose it through the authorized render view/mirror path. Add an opt-in volume/region policy input at the stored-SDF/composed-traversal seam, beginning with cutaway/visibility behavior. Keep edit application, collision, and mining outcome in the voxel world; the renderer only visualizes resulting state. Compare the opted-in region against the same scene without the policy.
4. **Then expand volume behavior.** Add density/extinction or fog only after its field semantics and output authority are declared; evaluate step limits, footprint/LOD bias, and mip fallback as independent policy values. Verify any coarse/mip path has a defined policy result rather than silently sampling a different material subset.
5. **Consider acceleration variants after semantics are stable.** Decide whether specialization constants, emitted recipe variants, or data-driven records best serve live variants. Revisit callable shaders only if a supported active RT path is established; avoid coupling the first material contract to dormant RT assets.

## 7. Owner questions

1. Who owns material identity and the response vocabulary: content-config/recipe outputs, a recipe GPU-domain system, or a render-runtime material table? Should the output contract include color, roughness, metalness, emission, and normals as one shared vocabulary?
2. Is recipe appearance selected per recipe, per material identity, or both? How should body tint relate to material channels?
3. Should the tug/asteroid slice use generated per-recipe shader variants via the already-optional bucketing path, or start data-driven with a shared shader? Which concrete recipe/content rows are the fixture?
4. For volume policies, should authored systems provide bounded data (density/extinction/step/LOD/cutaway) or a generated predicate/function? Which per-volume data is safe and available through the viewer-safe render projection?
5. For mining cut volumes, does the renderer receive the voxel world's post-edit geometry/region view, or should the voxel utility publish a derived cut-region representation? The R294 authority says edits are world-processed; the renderer must not apply the mining action itself.
6. Should Cornell-specific tie-breaks and palette shaders remain test fixture code, or be moved into external fixture data now that R106 makes the renderer/game boundary explicit?
