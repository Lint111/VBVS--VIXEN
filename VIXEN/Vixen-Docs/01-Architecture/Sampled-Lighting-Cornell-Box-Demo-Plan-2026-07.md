## Baked-vs-virtual pairing (added per user request, same session)

**This is not a novel idea in this codebase — real, working prior art already exists and should be reused, not reinvented.** `libraries/RenderGraph/tests/Nodes/test_baked_vs_virtual_parity.cpp` (Lazy-Procedural Delta-Baseline Inc0 M6 Task 14, DONE + Opus-validated, per the standing `lazy-procedural-delta-baseline-program` memory: "sphere IoU 0.84, CSG IoU 0.87 PASS") already proves the EXACT comparison this request wants, for arbitrary recipes: the SAME recipe rendered two ways —
- **(i) BAKED**: `BakeRecipeInstructionsToSdfWorld` → `BuildSdfBodyOctree` → `ConcatenateSdfWithMips` → `BodyOctreeSceneNode::SetRecipePool` (the octree/ESVO path every DDGI gate scene so far has used).
- **(ii) VIRTUAL**: `RecipeRegistry::Register` → `SpliceProceduralRecipesIntoSource` (runtime glslang-compiled uber-shader, per the Inc1 M5 "zero-bake GPU-direct" thesis) → `BodyOctreeSceneNode::SetOccupancyGrid` + a `PROVIDER_PROCEDURAL` `BodyInstanceGpu` — **zero bake calls**, proven via a call-counter assertion in the existing test.

That existing test is a HEADLESS silhouette-IoU gate (compares hit/miss coverage + a non-vacuity pixel-count floor, explicitly does NOT do a full pixel-color/GI comparison — its own file header states the depth/lighting comparison is out of scope for that specific test). This request wants the Cornell box's content baked via BOTH paths and rendered LIVE/VIEWABLE (not just IoU-compared headless) with DDGI active on both, so a human can visually compare GI quality/bounce-lighting fidelity across the two content-representation backends — genuinely new demo value on top of the existing parity test, not a duplicate of it.

**Consequence for the Cornell box's own construction**: every body in the box (5 walls, ceiling light, 1-2 objects) needs to be expressible as a REGISTERED RECIPE (via `RecipeRegistry`), not just a one-off baked lambda-SDF the way Inc4 M4's leak-gate scene bodies were built — the virtual/zero-bake path requires a real recipe program to splice into the uber-shader, not an ad-hoc C++ lambda only the bake path can consume. This means: (a) the walls need a real `RECIPE_BOX`-equivalent expressible in the recipe VM's own instruction set (check `SdfRecipes.h`/`RecipeOccupancy.h`'s existing opcode catalogue — Inc4 M4's inline lambda was fine for a bake-only scene but won't satisfy the virtual path here); (b) the ceiling light and objects likewise need real recipe programs, not `BakeRecipeToSdfWorldWithEmission`'s bake-only emission-lambda shortcut used previously — check whether the recipe VM already has an emission/emissive-material opcode, or whether emission needs to be handled as a SEPARATE per-instance material tag independent of the recipe geometry program (the two BAKED-path leak-gate bodies used a C++ emission LAMBDA specifically because that shortcut doesn't need to survive into a shader-spliced recipe program — the virtual path can't reuse it as-is).

**"Ideally visually identical" is a real design constraint, not just a nice property** — per the existing parity test's own documented tolerance (baked = voxelized 64³ narrow-band SDF with ~1-voxel edge antialiasing; virtual = exact analytic recipe-trace), expect SMALL geometric differences at silhouette edges even when everything is done correctly; the existing test's own `kIoUFloor` tolerance is the precedent for what "close enough" means quantitatively, if this demo also wants a numeric check (optional, see Gate below) rather than relying purely on visual judgment.

## Grounding from codebase investigation (2026-07-13)

**There is already a "cornell" scene, but it's the WRONG one — a different system entirely.** `VoxelGridNode::PARAM_SCENE_TYPE` defaults to `"cornell"` (`BuildRenderGraph.cpp:1131-1135`), resolved via `CashSystem::StringToSceneType` — this is the LEGACY procedural-grid test-scene path (`VoxelGridNode`/`CashSystem`), a wholly different code path from the live DDGI pipeline (`BodyOctreeSceneNode`/`TraceWorld`/`ProbeUpdate.comp`). It shares only the name with what this plan needs to build — confirm this is understood by any implementer so they don't assume the existing "cornell" scene type is reusable or even relevant; it must be ignored, not extended.

**The correct pattern to follow is Inc4 M4's own hand-built leak-test scene** (`BuildRenderGraph.cpp:2860-2903`, inside the `VIXEN_DDGI_LEAK_GATE_DEMO`/`VIXEN_DDGI_EDIT_LOOP_DEMO` block) — this is the live, real, Opus-validated precedent for "bake a small multi-body scene directly in `BuildRenderGraph.cpp` via lambda SDFs, feed the light-tree, wire it live." The exact reusable shape: `Vixen::SVO::BakeRecipeToSdfWorldWithEmission(RECIPE_SPHERE, center, params, kN, kBand, emissionLambda)` for an emissive light source; a hand-authored lambda SDF (there is no `RECIPE_BOX` in `SdfRecipes.h` — Inc4 M4 already hit this and hand-authored a box-distance function inline, `BuildRenderGraph.cpp:2879-2885`, reusable verbatim as a helper) baked via `Vixen::SVO::BakeSdfWorld(lambdaSdf, center, kN, kBand, depth)`; `BuildSdfBodyOctree` per body; `SerializeSdf`+`BakeAndAttachMipPool`+`BakeMipPool` for any body that should feed the light-tree; `BuildLightTreeCut` over the emissive body only (walls/objects are non-emissive, no light-tree entry needed for them).

**Multi-body concatenation precedent**: the leak-gate scene already builds TWO separate bodies (source sphere + wall box) and needs them both resident simultaneously — the exact same "concatenate several independently-baked bodies into one scene" shape a full Cornell box (5 walls + 1 ceiling light + 1-2 objects = 7-8 bodies) needs, just more bodies of the same kind, not a new mechanism.

**Historical naming precedent**: the graduation-thesis benchmark suite's own "cornell" scene (per `~/Downloads/VIXEN_benchmark_*` raw data, referenced in this program's own memory) was defined as "~5-15% density, empty box + 2 cubes" — worth matching that general shape/density for continuity with the codebase's own established sense of what "cornell" means, even though this is a new, unrelated implementation.

**DDGI-specific concern this scene must actually exercise**: per Inc4's own M4 finding (KI-030, ray-miss sentinel poisoning), a probe's visibility moment is computed from ray HITS only — an enclosed Cornell box (every probe ray eventually hits a wall, floor, or ceiling; very few/zero true misses for interior probes) is actually a GOOD stress scene for this, unlike the leak-gate scene's own thin-wall-in-open-space shape which deliberately has many sky-facing misses. Worth noting as a reason this scene has independent diagnostic value beyond just "looks nice," not only a cosmetic add.

## Self-Review

- **Why not extend the legacy "cornell" VoxelGridNode scene instead of building new?** It's on an entirely different code path (`VoxelGridNode`/`CashSystem`, not `BodyOctreeSceneNode`) that DDGI's own pipeline (`TraceWorld`, `ProbeUpdate.comp`, the light-tree) doesn't read from at all — extending it would produce a scene DDGI literally cannot see.
- **Why must both variants share ONE scene-definition source rather than being independently authored?** "Ideally visually identical" is only actually enforced if both variants are baked FROM the same numbers — two independently hand-tuned scenes that happen to look similar would not actually test what this comparison is for (does the content-representation backend, not the scene author's own consistency, affect GI quality).
- **Why does this now require real recipe programs instead of Inc4 M4's simpler inline-lambda approach?** The virtual/zero-bake path only knows how to render REGISTERED recipes (spliced into the uber-shader at compile time) — a C++ lambda that only the CPU-side bake function can evaluate has no meaning to that path. This is a real, load-bearing constraint the baked-only version of this plan didn't have to satisfy.
- **Why is this scoped as one milestone (two variants) rather than two separate increments?** They share a scene definition, camera, probe grid, and gate structure by design — splitting them would duplicate almost everything and make "are they actually comparable" harder to guarantee, not easier.
- **Deliberate non-scope:** any change to DDGI's own algorithms; a formal PSNR/numeric image-comparison gate (optional stretch, not required to close this milestone); multiple camera angles/animated fly-through; extending this pairing pattern to OTHER existing DDGI demo scenes (leak-gate/edit-loop) — those already serve their own proven purposes as baked-only ablation gates, out of scope to also dual-render them here.

Because `rayAABBIntersection`/`TraceWorld.glsl` always culls against an octree's FULL local `[0,1]³` cube (`OctreeConfig.gridMin/gridMax` are recorded but never read by the traversal shader), every body's real-world AABB was the SAME oversized `[0,64)³` cube — and the camera (world Z≈50, per `kCameraOrbitDistance=34` from box-center Z=16) sat INSIDE all eight of them simultaneously, defeating the front-to-back reject and corrupting the traversal. **Fix:** gave each body its own TIGHT per-body bake grid (`kWallN=32` for the 5 walls, `kSmallN=16` for the light/objects), each with its own `worldPos`/`renderScale`/`bakeCenter` chosen so recipes stay authored in `CornellBoxSceneDefinition.h`'s own absolute world-unit coordinates (verified algebraically before landing: `worldPos = bodyWorldCenter - n/2`, `renderScale = n/kWorldGridSize`, `bakeCenter = n/2 - bodyWorldCenter` composes to an exact identity map). This mirrors the established multi-body pattern already used by `VIXEN_DDGI_LEAK_GATE_DEMO` and `VIXEN_TIER_OBSERVABLE_DEMO` — the single-shared-grid approach was the outlier, not a new mechanism.
  - **Root cause #2 (real shader bug in shared traversal code, fixed in `TraceWorld.glsl`):** after fixing #1, hits still landed on a suspicious exact flat plane. A GPU readback extended to report the winning body-instance index (via `HitRecord`'s spare padding field — no new SSBO binding needed) proved the hit distances were wrong by EXACTLY a factor of `inst.renderScale`: a `renderScale=3.2` body reported `hitT=5.625` for a ray whose true entry distance was `18.0` (`5.625*3.2==18.0` exactly, confirmed both by hand-derivation and live GPU readback). `TraceWorld.glsl`/`SceneBindings.glsl`'s shared ESVO instanced-traversal code computes `hitT` as a parameter along `instDir` (`rayDir/renderScale`) but its own comment incorrectly asserted `instDir` was unit-length and that the returned `hitT` was already true world distance — true only when `renderScale==1`, which every DDGI demo before this one happened to use, making the bug invisible until this scene's first non-unit `renderScale`. **Fix:** multiply `hitT` (and the front-to-back early-reject's own copy of the same math, `entryTWorld`) by `inst.renderScale` at both of `TraceWorld.glsl`'s call sites. - **M1 round 5 (2026-07-14): SECOND ROOT CAUSE FOUND + FIXED — thin walls no longer bake as solid overlapping cubes.** User feedback on round 4's screenshot: "the generated structure scale is out of whack, its many large cubes overlapping instead of a proper room like cornell box shape."
