# BodyOctreeSceneNode — Intermittent Baked-Path Hit Corruption — Bug Report (2026-07)

**Status (updated Round 5, Opus, 2026-07-15):** Confirmed real, reproducible-but-intermittent. **ROOT-CAUSE MECHANISM NOW IDENTIFIED with direct synchronization-validation evidence** (not yet fixed — the fix is a high-blast-radius change to the render-graph's core frame-sync discipline, deliberately NOT attempted speculatively this round). It is **NOT a `BodyOctreeSceneNode`-specific bug at all** — it is a general render-graph command-buffer/descriptor-set **reuse-while-still-pending** hazard (the per-image/per-flight fence discipline is insufficient) that the BAKED path's heavier, longer-running ESVO compute dispatch turns into *visible* corruption while the VIRTUAL path's cheap analytic trace usually finishes before the overwrite lands. See "Round 5 root cause" below. All four of the prior rounds' leads (shell double-buffer, lazy residency, renderScale regression, per-body addressing) are confirmed NOT the cause.

## Summary

Running the same `VIXEN.exe` binary against the same scene (`VIXEN_DDGI_CORNELL_BAKED_DEMO=1`, no code change between runs) produces **different results on different runs**: some runs render correctly, others show corrupted ray-hit data — world-space hit positions wildly outside any legitimate scene bounds (e.g. `worldPos.z=-51.2` when no geometry exists past `z=4`), concentrated in a spatially contiguous cluster of screen pixels. This is a genuine non-determinism in the baked/octree rendering path, not a geometry-authoring bug (that category has been independently ruled out — see below).

**Only the BAKED (octree/`BodyOctreeSceneNode`) path is affected.** The VIRTUAL (zero-bake, `PROVIDER_PROCEDURAL`) path renders the identical shared geometry cleanly and deterministically across every run tested. This strongly implicates something specific to `BodyOctreeSceneNode`'s own machinery — instance upload, brick residency, or (the leading untested lead) its double-buffered "Surface-Shell ESVO cache" — rather than anything in the scene content, the shared traversal shader (`TraceWorld.glsl`), or DDGI itself.

## How this was found

Discovered 2026-07-14 while shipping the Sampled Lighting Cornell Box GI reference-scene demo (`Sampled-Lighting-Cornell-Box-Demo-Plan-2026-07.md`). That demo's own M1/M2 milestones had already passed 3 rounds of Opus validation and been merged to `main` (`1be4efdb`) before the user looked critically at the actual screenshots (not just "is there a recognizable box shape") and caught real geometry incoherence in both variants. A follow-up "M3" investigation (4 rounds, branch `fix/cornell-geometry-coherence`, worktree `.claude/worktrees/cornell-geom-fix-m3`) fixed 3 real, confirmed geometry-authoring bugs (wall-span gaps, a double-applied bake-center offset, an open-face asymmetry error) — after which the VIRTUAL variant became fully clean and deterministic, but the BAKED variant kept exhibiting this separate, intermittent corruption. This doc captures that residual finding on its own, since it's a bug in shared engine code (`BodyOctreeSceneNode`), not something specific to the Cornell demo — the demo just happened to be the first scene to expose it visibly (8 bodies registered together, unlike prior single/dual-body DDGI demo scenes).

## What's been ruled out (with live evidence, not just reasoning)

- **Geometry authoring/placement.** M3 round 2 unified both demo variants onto ONE shared world-space `SdfInstruction` source (`BuildCornellWorldSpaceBodies()`, `BuildRenderGraph.cpp`) — literally the same geometry data feeds both the baked and virtual paths now. The virtual path renders this correctly and deterministically every time; the baked path does not. Since the source data is byte-identical, the bug cannot be in how the geometry is authored or placed — it must be baked-path-specific machinery.
- **A regression of the known `hitT *= inst.renderScale` fix** (the bug class M1 rounds 4/6 found and fixed in `TraceWorld`/`TraceWorldShadow`). Both call sites were re-confirmed present and unmodified in current code. The corrupted hits' `hitT` values DO show the exact numeric signature of a missing renderScale correction (dividing by `kWallRenderScale` lands the value back in the correct range) — but the correction code is present, so this reads more like the correction not being RELIABLY APPLIED (a data race reading stale/wrong `renderScale` for that instance) than a missing correction.
- **Lazy brick residency / async brick-upload latency.** The Cornell baked scene's bodies are all mip-capable, so `DeriveResidencyDefault` computes LAZY residency by default (background async brick upload, `BodyOctreeSceneNode::PollBrickUploadCompletion`) unless `RequestBrickResidency(true)` is called explicitly — a real, previously-hit bug class (`VIXEN_TIER_OBSERVABLE_DEMO` M8 Task 21 hit and fixed exactly this). This was a strong, plausible lead and was tested directly: adding `RequestBrickResidency(true)` did NOT fix the corruption — it got WORSE (a higher out-of-bounds ratio), AND the culprit instance shifted from `instIdx=2` (backWall) to `instIdx=4` (ceiling) between the residency-off and residency-on runs. A residency-timing bug tied to one body's async upload should not behave this way — this decisively rules out residency latency as the (sole) cause.

## What's confirmed (with live evidence)

- **Genuinely non-deterministic across runs of the identical binary.** 3 back-to-back runs of the same `VIXEN.exe`, same scene, same env vars: run 1 clean (98.5% hit rate, 0 out-of-bounds hits), run 2 broken (33.6% hit rate, 1647 out-of-bounds hits), run 3 clean again with numbers byte-identical to run 1. This is not a flaky measurement — it's the render itself producing different GPU-committed results from identical inputs.
- **When broken, the culprit is NOT fixed to one instance.** Across different broken runs, the corrupted hits have been attributed to `instIdx=2` (backWall) in some runs and `instIdx=4` (ceiling) in another (the residency-test run). This argues against a bug specific to one body's data/buffer slot.
- **When broken, the corrupted pixels cluster in a consistent SCREEN region**, not scattered randomly — roughly the same rows/columns (near where the ceiling and back-wall's screen-space silhouettes meet) across multiple broken runs, even as the underlying instIdx varied. This is the most specific, and least-explored, lead: something about the ray-geometry situation for that particular screen region/dispatch tile (e.g. rays nearly grazing an instance-AABB seam) may be a contributing or triggering factor, independent of which instance ends up reporting the bad data.
- **Corrupted hits show a `hitT`-scaling signature** consistent with a `renderScale` correction not being applied for the affected sample, even though the correction code itself is present and correct in the shader source — pointing at a data race (the GPU reading a stale/wrong `renderScale` value for an instance on some frames) rather than a missing code path.

## Leading untested hypothesis: the Surface-Shell ESVO cache double-buffer

> **SUPERSEDED (Round 5):** this hypothesis was DISPROVEN — see the "Round 5" sections below. The shell double-buffer is dead code (`dirtyBricks_` is never populated) and read-only in every pass. The actual root cause is a render-graph command-buffer/descriptor-set reuse-while-pending hazard; jump to **"Round 5 root cause"** below. This section is kept for the investigation trail.

`BodyOctreeSceneNode.cpp` has a double-buffered "Surface-Shell ESVO cache" mechanism (`shellCache_[0]`/`[1]`, `shellDataBuffer_[readSlot]`/`[writeSlot]`, slot selection via `rawFrame & 1` in `ExecuteImpl`) that runs unconditionally for any scene with real SDF channel data — true for the Cornell scene. Its own source comments already reason explicitly about read/write-slot hazards:

> "Because the two GPU slots are DISTINCT VkBuffer objects, a render reading slot N and this revalidate writing slot N+1 touch disjoint `Resource*`; the FrameSyncScheduler (pointer-identity hazard keying) inserts no barrier between them." (`BodyOctreeSceneNode.cpp` ~line 372)

This reasoning is deliberate (the two buffers are genuinely disjoint resources, no barrier is needed IF the read/write slot selection is always correct) — but if there's an edge case where the wrong slot is selected, or a revalidate races the render's own read of the "current" slot, this would produce exactly the observed symptom class: correct data most of the time, occasionally reading a slot that hasn't been fully written yet or was written for a different frame's state.

**This was identified but NOT traced in the 4 investigation rounds so far** — flagged as the most promising remaining lead specifically because (a) it's a genuinely complex, actively-double-buffered mechanism the investigation hadn't looked at until the last round, (b) its own comments already show the authors reasoning carefully about a hazard in this exact shape, and (c) unlike the two disproven hypotheses, nobody has yet gathered direct evidence for or against it.

## Round 5 (Opus, 2026-07-14/15): the leading hypothesis is DISPROVEN by static analysis, plus four more mechanisms eliminated

*(This "Round 5" spans two sub-parts: the static-analysis elimination immediately below, then the "Round 5 root cause" section further down where synchronization validation confirmed the actual mechanism.)*

A dedicated Opus round traced the full `BodyOctreeSceneNode` state machine, the `BatchedUploader` submission path, the `FrameSyncScheduler` hazard model, the descriptor-set lifecycle, and the shader's ESVO leaf dispatch. Result: **every GPU-synchronization mechanism that could plausibly produce this corruption for the Cornell BAKED scene's SPECIFIC configuration is eliminated.** Details, each with the code evidence that rules it out:

1. **The Surface-Shell double-buffer (the "leading untested lead") is DEAD CODE for every scene, not just Cornell.** `dirtyBricks_` is the ONLY thing that triggers the write-slot revalidate (`ExecuteImpl`, gated on `!dirtyBricks_.empty()`), and `dirtyBricks_` is **never populated anywhere in the entire codebase** (`grep` confirms: declared, read, and `.clear()`ed, but never pushed to). So after the Compile-time bootstrap (`DeriveShellCache` writes BOTH slots byte-identically), the write slot is never touched again. Both GPU shell slots hold **byte-identical** data for the whole run; the `rawFrame&1` read-slot selection is choosing between two identical buffers. Furthermore the shell data buffers are **read-only in every consumer pass** (trace, direct-lighting, spatial-reuse, probe-update all `Connect` them as inputs; no compute pass writes them) — so there is no writer to form a RAW hazard with, and the "no barrier between reader and writer" comment describes a hazard that cannot occur. This lead is closed.

2. **The lazy brick-upload async race does NOT fire for this scene.** All 8 Cornell bodies are mip-capable, so `DeriveResidencyDefault` returns LAZY (`residencyRequested_ = false`) and the scene never calls `RequestBrickResidency` (the round-4 `RequestBrickResidency(true)` trial was reverted). With `residencyRequested_ == false`: `UploadBrickPool` early-returns as a no-op, so `pendingBrickUploadHandle_` stays invalid, so `PollBrickUploadCompletion` never queues the config re-upload either. **There is NO per-frame async `vkCmdCopyBuffer` into any render-read buffer for the LAZY Cornell scene.** (This also explains round 4's finding that forcing residency ON made it *worse* — that path DOES add the async brick/config copy race on top of the base bug, a second corruption source, not the base one.)

3. **The uninitialized brick buffer (binding 2, allocated but `nullptr`-filled under LAZY) is never read.** The ESVO leaf dispatch (`SceneBindings.glsl` ~line 884) checks `octreeConfig.brickResident == 0u` BEFORE the `formatId` dispatch and takes the **mip-fallback** path (`shadeFromMipSample`, reading the populated `mipPool` at binding 13) — it explicitly does NOT march the un-uploaded brick buffer. The comment there names this exact hazard ("would read zero-filled/garbage buffer contents"). So the primary visible hit for LAZY Cornell resolves via mip samples, deterministic data.

4. **The instance ring + shell slot host writes are guarded by the flight fence.** `CURRENT_FRAME_INDEX` is the FLIGHT index (`currentFrameIndex = (currentFrameIndex+1) % MAX_FRAMES_IN_FLIGHT`), and `FrameSyncNode::ExecuteImpl` waits `frameSyncData[currentFrameIndex].inFlightFence` BEFORE the graph executes downstream nodes — so `ExecuteImpl`'s write into ring slot `rawFrame%4` / shell slot `rawFrame&1` targets a slot whose prior GPU work is already complete.

5. **Descriptor sets are guarded by the SwapChainNode per-image fence.** Descriptor sets are keyed by swapchain IMAGE index and updated in place each frame (no `UPDATE_AFTER_BIND`); `SwapChainNode` waits `imagesInFlight[currentImageIndex]` before that image's descriptors are overwritten (the wait that was added to fix `VUID-vkUpdateDescriptorSets-None-03047`).

### Architectural fragility found (documented, not yet proven causal)

There is a real **period mismatch** with no common divisor: descriptor sets are keyed by swapchain image count (typically **3**), the shell buffers ping-pong by `rawFrame&1` (**2** physical slots), and the instance ring cycles by `rawFrame%4` (**4** slots). Which physical buffer is baked into which per-image descriptor set therefore rotates frame-to-frame, and correctness rests ENTIRELY on `SwapChainNode`'s per-image `vkWaitForFences` (`SwapChainNode.cpp` ~line 197) actually gating every one of the four independent gatherer→DescriptorSetNode chains that source these buffers. This is fragile but appears correctly guarded in steady state — it is called out here as the most likely place a subtle, timing-dependent breakage (e.g. a frame where that wait is skipped/reordered, or a swapchain image count that changes the period) could live, since it is the single load-bearing synchronization point for the whole ping-pong scheme, and the corruption's run-to-run non-determinism + screen-region clustering is consistent with an occasional descriptor/buffer-vs-fence period desync rather than a deterministic addressing error.

### What this means for the remaining search

The run-to-run non-determinism, from byte-identical CPU inputs, with NO per-frame async GPU write and all host writes fence-guarded, most strongly indicates either (a) a genuine but intermittent break in the per-image-fence guard above (a real GPU read-vs-write-of-a-buffer-being-reused hazard the `FrameSyncScheduler` cannot model because the buffer handle it would key on CHANGES every frame), or (b) reading GPU memory that is uninitialized on SOME frames due to that period desync. The next step is empirical and direct: **Vulkan synchronization validation** (force-enabled via the loader's `VK_INSTANCE_LAYERS` + `VK_LAYER_ENABLES` sync-val feature, independent of the app's own compile-time validation gate) to flag the exact missing barrier if one exists, run against a known-broken capture, plus a 15-run `[CornellDiag]` failure-rate sample to confirm the reproduction rate and whether the screen-region/instIdx pattern holds.

## Round 5 root cause (Opus, 2026-07-15): command-buffer + descriptor-set REUSE-WHILE-PENDING, exposed by the BAKED path's longer compute

Both the empirical sample and synchronization validation were run. Findings:

**Failure-rate sample (baked, current machine state): 8/8 clean, byte-identical.** Zero reproductions in 8 back-to-back runs when the machine was quiet — vs. the prior rounds' readily-reproduced ~1/3 failure rate (those rounds ran with many agents hammering the machine). **The reproduction rate correlates with machine load.** That load-dependence is itself a strong positive signature of a GPU-scheduling race (a missing/insufficient synchronization the driver "gets away with" under favorable timing), not a deterministic logic error — and it is why the clean runs are byte-identical (correct when the race window doesn't overlap) while broken runs are wildly off.

**Synchronization validation (force-enabled via `VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation` + `VK_LAYER_ENABLES=VK_VALIDATION_FEATURE_ENABLE_SYNCHRONIZATION_VALIDATION_EXT`; sync-val output reaches stdout via the layer's own default reporter, which the app captures — no app-side debug-utils messenger needed) fired a coherent CLUSTER of frame-synchronization violations, throughout the run (not just startup), all pointing at the same mechanism:**

- **`VUID-vkUpdateDescriptorSets-None-03047` (20×)** — the decisive one. Verbatim: *"VkDescriptorSet 0xf5… is in use by VkCommandBuffer 0x1cfc4879b70"* while `vkUpdateDescriptorSets` overwrites its bindings (dstBinding 0,1,…). The descriptor set carrying the compute pass's buffer bindings (octree nodes/bricks/config/instance/shell) is being **rewritten while a still-pending GPU submission is reading it**, without `UPDATE_AFTER_BIND`/`UPDATE_UNUSED_WHILE_PENDING`.
- **`VUID-vkBeginCommandBuffer-commandBuffer-00049` (20×)** — the SAME `VkCommandBuffer 0x1cfc4879b70` is re-recorded *"before it has completed. You must check command buffer fence before this call."*
- **`VUID-vkQueueSubmit2-commandBuffer-03875` (20×)** — that same command buffer *"is already in use and is not marked for simultaneous use"* at re-submit.
- **`VUID-vkResetFences-pFences-01123`, `VUID-vkAcquireNextImageKHR-semaphore-01779`, `VUID-vkQueueSubmit2-semaphore-03868` (20× each)** — fence reset / semaphore reuse while still in use, the rest of the same reuse-while-pending family.

**These are the very VUIDs `SwapChainNode.cpp`'s per-image `imagesInFlight` fence-wait block (≈ line 181-204) claims in its own comment to have FIXED — sync-val proves they still fire.** Command buffers and descriptor sets are keyed by swapchain **image** index (typically 3), but the fence actually waited each frame is the **per-flight** fence (`FrameSyncNode`, `MAX_FRAMES_IN_FLIGHT = 4`); with 4 flights vs 3 images the two rings desync and the per-flight fence signalling does NOT prove that *this image's* command buffer / descriptor set has finished. The `imagesInFlight` per-image wait was meant to close that gap but demonstrably does not for every consumer (`ComputeDispatchNode::ExecuteImpl` re-records `commandBuffers.GetValue(imageIndex)` and its DescriptorSetNode rewrites the per-image set each frame, guarded only by the per-flight fence path).

**Why BAKED corrupts but VIRTUAL does not — with direct evidence.** Sync-val on the VIRTUAL variant, run to the same frame count, showed the **identical descriptor/command-buffer VUID cluster (same 20× counts)** — confirming the reuse-while-pending violation is **general, not baked-specific** — BUT the VIRTUAL run had **0× `SYNC-HAZARD-WRITE-AFTER-PRESENT`** while the BAKED run had **10×**. The discriminator is *duration*: the BAKED ESVO compute dispatch (heavy octree traversal reading the per-instance config/`renderScale`/shell bindings) runs far longer on the GPU than VIRTUAL's cheap analytic sphere-trace, so the window in which a still-pending read overlaps the descriptor/command-buffer overwrite is much wider on the baked path. When that window overlaps, the compute reads torn/stale bindings — the wrong instance's `octreeIndex`/`renderScale`/`worldToLocal` — producing exactly the observed symptom: a hit whose `hitT` is off by a `renderScale` factor, attributed to a shifting instance, clustered in the screen region that instance projects to, intermittent, and load-dependent. VIRTUAL, finishing its compute fast, almost always completes its reads before the overwrite lands, so the same latent violation stays invisible.

This ties together every previously-unexplained fact: run-to-run non-determinism from identical inputs (a timing race), byte-identical clean runs (no overlap → correct), the `renderScale`-scaled `hitT` (a torn per-instance binding read), the shifting culprit `instIdx` (which instance's binding was torn depends on timing), the screen-region clustering (that instance's projection), the load-dependence (wider overlap under scheduling jitter), and BAKED-only visibility (longer compute → wider window).

### The fix (NOT applied this round — high blast radius, deliberately deferred to a focused round)

The correct fix is in the render-graph core frame-sync discipline, not in `BodyOctreeSceneNode` or the Cornell scene — it affects **every** scene and every frame, so it must be done carefully with sync-val as the green-light gate, not bolted on speculatively (the task that surfaced this explicitly warned against a third unverified guess). Candidate directions, in rough order of preference:
1. **Make the per-image resources actually wait on the per-image fence.** Ensure every consumer that reuses an image-indexed command buffer or descriptor set (`ComputeDispatchNode`, `DescriptorSetNode`, geometry/UI render nodes) blocks on the fence that last guarded *that image index* before re-recording / `vkUpdateDescriptorSets`, closing the flight-vs-image desync. This is what `SwapChainNode`'s `imagesInFlight` wait intends; sync-val shows it is not sufficient as wired — find why the wait isn't gating these specific reuses (ordering of the wait vs. the re-record across nodes, or a consumer that doesn't observe it).
2. **Double-buffer the descriptor sets / command buffers to `MAX_FRAMES_IN_FLIGHT` (4) instead of image count (3)**, so the flight fence (which IS waited) genuinely guards them — removes the period mismatch at its source.
3. **Mark the churned descriptor bindings `VK_DESCRIPTOR_BINDING_UPDATE_UNUSED_WHILE_PENDING_BIT`** (requires `VK_EXT_descriptor_indexing`) so the per-frame rebind is legal while pending — narrower, addresses `03047` specifically but not the command-buffer-reuse VUIDs.

The `WRITE-AFTER-PRESENT` layout-transition-vs-present hazard is part of the same insufficient-sync family and should be fixed alongside (it is the visible-image analogue of the buffer-read race).

**Verification gate for whichever fix is chosen:** re-run the exact sync-val capture (both baked and virtual) and confirm the `vkUpdateDescriptorSets-03047` / `vkBeginCommandBuffer-00049` / `vkQueueSubmit2-03875` / `WRITE-AFTER-PRESENT` cluster is GONE (not merely reduced), then re-run the baked `[CornellDiag]` sample many times **under deliberate machine load** (the condition that reproduces it) and confirm 0 out-of-bounds hits across the whole sample. A quiet-machine clean sample is NOT sufficient evidence the fix worked, given the load-dependence established above.

## Suggested next steps, in order of expected value

> **SUPERSEDED (Round 5):** steps 1-3 below were the pre-root-cause plan; step 3 (synchronization validation) is what actually cracked it — see "Round 5 root cause" above for the result and the real remaining work (the fix + its verification gate). Kept for the trail.

1. **Trace `DeriveShellCache`/`RevalidateShellBricks`/`UploadShellSlot`** (`BodyOctreeSceneNode.cpp`, roughly lines 803-950) with the screen-region correlation in mind — check whether the Cornell scene's shell-derive output could plausibly disagree between CPU slot 0 and slot 1 on a given frame, or whether `ExecuteImpl`'s `rawFrame & 1` read-slot selection could pick a slot that a revalidate is still mid-write to under some timing.
2. **Establish a real failure rate**, not just "it can happen" — run the baked demo 10+ times back-to-back with the existing `[CornellDiag]` diagnostic (out-of-bounds scan + `instIdx` reporting, already committed and left in place — see Diagnostic tooling below) and record how often it fails, whether the failing screen-region stays consistent, and whether the culprit instance is genuinely random or has some pattern across a larger sample than the 3-4 runs done so far.
3. **Use GPU-side tooling instead of inferring from CPU-side readback alone** — Vulkan synchronization validation (`VK_LAYER_KHRONOS_synchronization2` / sync-val) would directly flag a missing barrier if that's the mechanism; a RenderDoc capture diff between a clean run and a broken run would show the actual command submission order and buffer contents at the moment of the bad read, which is a much more direct answer than reasoning from rendered pixel output.
4. **Do not attempt a speculative fix without one of the above.** Two speculative-but-plausible hypotheses (missing renderScale correction regression, lazy residency) were both tested directly and disproven — this bug is more subtle than either looked at first, and a third guess without better evidence risks the same outcome (or worse, masking the symptom without fixing the cause).

## Diagnostic tooling already in place

Left in the codebase (not stripped, since it will be needed again): `VulkanGraphApplication.cpp`'s `[CornellDiag]` block (env-gated behind `VIXEN_DDGI_CORNELL_BAKED_DEMO`, fires at tick 150) scans the full `HitRecord` buffer for out-of-bounds `worldPos` and reports the exact pixel plus which instance won the hit. `TraceWorld.glsl` carries a `WorldHit.instIdx` field (both commit sites) threaded through `HitRecord._pad0[0]` (`BodyInstanceRayMarch.comp`) to make this possible — a real spare struct field, no layout break (`test_hitrecord_sdi_parity.cpp`'s own layout assert is unaffected). Whoever picks this up can re-run the exact same diagnostic immediately without re-deriving it.
