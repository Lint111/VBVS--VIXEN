# Sampled Lighting Inc6 — Sparse-Dispatch Amortization (Mechanism B) — Plan (2026-07)

**Trigger:** Inc5's own honestly-caveated finding — amortized probe updates (`amortizationFactor=8`) reduced cost in the CONFIRMED-REAL direction but SUB-LINEARLY vs. the naive 1/F prediction (measured 6.14→3.22→2.15ms for F=1/4/8 vs. predicted 6.14→1.54→0.77ms). Root-caused in conversation (2026-07-13, user-driven): Inc5's mechanism (dispatch ALL `probeCount` workgroups every frame, early-out inside 7/8 of them) still pays per-workgroup GPU-side overhead — launch/scheduling, shared-memory setup, `barrier()` sync points, the `ProbeGridConfig` SSBO read — for every skipped probe, every frame, regardless of `amortizationFactor`. Only the expensive part (`TraceWorld`/ray-cast) actually shrinks by 1/F; the fixed per-workgroup overhead does not. This is the GPU-internal analog of the classic "moving N× the data/setup to use only 1/N of it" waste pattern — same shape, different resource (workgroup dispatch/scheduling, not PCIe bandwidth).

**Base:** whatever main is at when this launches (Inc5 merged at `e6a3ec3c`).

**Scope:** replace Inc5's "dispatch-all, early-out-inside" amortization mechanism with the plan's own originally-noted mechanism (b): dispatch ONLY the active `probeCount/amortizationFactor` workgroups each frame, via a stride-based `gl_WorkGroupID` remap — eliminating per-workgroup overhead entirely for skipped probes, not just skipping their expensive inner work. Then re-run the SAME A/B measurement Inc5 used, to see whether this closes the gap toward the naive 1/F prediction.

## Grounding from codebase investigation (2026-07-13)

**`amortizationFactor` is a build-time-only value today — this makes the fix small.** Confirmed via `ProbeGridConfigNode.cpp`: the shipped default (`8u`) and the `VIXEN_DDGI_AMORTIZATION_FACTOR` env override are both read ONCE at graph-build time (`MakeDefaultProbeGridConfig`), never mutated at runtime. This means the dispatch-X parameter for `probeUpdateNode` — currently `kProbeUpdateDefaultProbeCount` (`BuildRenderGraph.cpp:986-990`, a `constexpr` set once via `SetParameter(PARAM_DISPATCH_X, ...)`) — can simply be recomputed as `kProbeUpdateDefaultProbeCount / amortizationFactor` at the SAME build-time call site. No live/per-frame-dynamic dispatch-dimension machinery needs to be built; this is NOT the architectural complication it could have been.

**Shader-side remap is a small, local change.** Today `ProbeUpdate.comp`'s `main()` reads `uint probeIndex = gl_WorkGroupID.x;` directly (the dispatched workgroup index IS the probe index). The fix: `uint probeIndex = gl_WorkGroupID.x * amortizationFactor + (frameCounter % amortizationFactor);` — a pure arithmetic remap, no new buffer/binding needed (both `amortizationFactor` and `frameCounter` are already-bound `ProbeGridConfig` fields from Inc5 M1). This replaces the THIRD early-out Inc5 M1 added (`if (amortizationFactor>1u && (probeIndex%F)!=(frameCounter%F)) return;`) — that early-out becomes DEAD CODE once the dispatch itself only ever produces active-slot probe indices; it should be REMOVED, not left redundant, to keep the shader honest about what's actually happening.

**What must NOT change**: every other early-out, the leak-gate self-test gather block, the shading/hysteresis-blend logic, the atlas-write addressing — none of this cares HOW a probe's index arrived, only that `probeIndex` is a valid probe. Since the new dispatch always produces exactly `probeCount/F` valid, in-range, correctly-rotating indices (never an out-of-range or duplicate index across one rotation-slot's dispatch), the existing `if (probeIndex >= probeCount) return;` early-out also becomes dead for the common case but should stay as a defensive bound (cheap, harmless, guards against `probeCount` not being evenly divisible by `amortizationFactor` — see Non-integer-division note below).

**Non-integer-division edge case, must be handled explicitly, not ignored.** `probeCount / amortizationFactor` in integer arithmetic truncates — e.g. `probeCount=512, F=8` divides evenly (64), but a future config with `probeCount=500, F=8` would dispatch only 62 workgroups (`500/8=62`), leaving `500 - 62*8 = 4` probes NEVER reached by any rotation slot's dispatch across a full F-tick cycle (they'd only be covered if `gl_WorkGroupID.x*F+slot` happens to land in range, which it structurally can't for the highest few indices when there's a remainder). This must be decided explicitly: either (a) round the dispatch count UP (`ceil(probeCount/F)`) and rely on the existing `probeIndex >= probeCount` bound-check to harmlessly discard the occasional over-dispatch, ensuring every probe IS reachable across the full rotation — the correct, recommended fix — or (b) document that `probeCount` must be exactly divisible by `amortizationFactor` and assert/warn if not. Prefer (a): it's a one-line `ceil` change and fully closes the coverage gap, and the plan's own default (`8x8x8=512`, divisible by 8) means this is currently latent but must not silently regress a future non-divisible grid config.

**Regression-relevant fact carried over from Inc5's own gate infrastructure**: `VIXEN_DDGI_AMORTIZATION_FACTOR=1` must still be a genuine byte-identical escape hatch after this change — at F=1, `probeIndex = gl_WorkGroupID.x * 1 + (frameCounter % 1) = gl_WorkGroupID.x + 0 = gl_WorkGroupID.x`, i.e. degenerates to today's direct mapping, dispatched at the full `probeCount` (since `probeCount/1 = probeCount`) — verify this arithmetic identity explicitly, the same discipline Inc5 M1's own validator applied to its own degenerate case.

## Self-Review

- **Why is this its own small increment rather than reopening Inc5?** Inc5 is merged, validated, and its own honest conclusion ("direction confirmed, magnitude sub-linear, mechanism B was the known fallback") is exactly what motivates this follow-up — reopening a closed, validated increment to swap its core mechanism would be worse practice than a clean, small, targeted follow-up that can be independently gated and, if it doesn't pan out, reverted without touching Inc5's own already-proven state.
- **Why remove the now-dead early-out rather than leave it as defense-in-depth?** A conditional that can structurally never fire (because the dispatch itself now only ever produces active-slot indices) is worse than no conditional at all — it reads as "this is still doing something" to a future maintainer, when it isn't. Dead code that LOOKS load-bearing is a durable maintenance hazard this program's own established `search-and-replace`/cleanup discipline should avoid introducing.
- **Deliberate non-scope:** any change to the convergence math (unchanged — a probe still updates once every F ticks, just via a different dispatch path); any change to `raysPerProbe`/grid density (Inc5's own already-honest "not enough clean data" conclusion stands, untouched by this mechanism swap); HW-RT acceleration or multi-queue (both separate, larger, deferred per `DDGI-HWRT-Acceleration-And-MultiQueue-Direction-2026-07.md`).
- **Biggest risk:** the non-integer-division edge case (probeCount not evenly divisible by amortizationFactor) — silently under-covering probes is a real correctness bug, not just a performance nuance, if the `ceil()` fix isn't applied correctly; this needs its own explicit live verification (e.g. deliberately test a non-divisible grid config, not just the shipped 512/8=64 case which happens to divide evenly and would hide the bug).
