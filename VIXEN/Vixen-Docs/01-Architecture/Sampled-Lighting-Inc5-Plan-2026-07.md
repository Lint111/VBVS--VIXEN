# Sampled Lighting Inc5 — Amortized Probe Update + Tuned Defaults — Plan (2026-07)

**Spec:** `DDGI-HWRT-Acceleration-And-MultiQueue-Direction-2026-07.md` §2 ("Inc-next: universal fix, works on every machine"). Trigger: Inc4's own M6/M7 finding — shipped defaults (raysPerProbe=64, 8×8×8=512-probe grid) cost the probe-update pass ~20-24ms/frame ALONE, exceeding the entire 16.6ms (60fps) budget by itself, twice-independently measured.

**Base:** main `ad17d45c` (Inc4 DDGI merged + pushed).

**Scope:** reduce DDGI probe-update GPU cost via three independent, composable levers — amortized per-probe update scheduling (update a fraction of probes/frame, round-robin), tuned `raysPerProbe` default, tuned grid density (`countX/Y/Z`) — targeting the pass fitting comfortably inside a fair share of the 16.6ms budget alongside Inc1-3's already-shipped costs, WITHOUT touching probe-update's shading correctness (leak rejection, Chebyshev math, hysteresis blend direction) or the M5 shade-pass gather, all already Opus-validated and out of scope for re-litigation here. NOT in scope: hardware ray-query acceleration (a separate, later increment per the direction doc §3) or multi-queue (§4, deferred further still).

## Grounding from codebase investigation (2026-07-13)

**The dispatch shape makes amortization mechanically simple.** `ProbeUpdate.comp` is one-workgroup-per-probe, dispatched as `(probeCount, 1, 1)` workgroups (`BuildRenderGraph.cpp:986-992`, `kProbeUpdateDefaultProbeCount` = a build-time constant `SetParameter(PARAM_DISPATCH_X, ...)` call — not live/per-frame-varying today). `ProbeUpdate.comp:329-334`'s `main()` already has an unconditional-return early-out shape (`probeGridConfig.probeGridEnabled == 0u`, `probeIndex >= probeCount`) that a per-frame active-subset test can extend with zero structural change to the shader below that point — every line of shading logic (ray cast, light-tree sample, hysteresis blend, atlas write) is already gated behind reaching past the early returns, so an amortization skip is a THIRD early-out in the same family, not new control flow threaded through the pass.

**Mechanism chosen: modulo-based active-subset early-out, not a smaller dispatch.** Two mechanisms were considered (per the direction doc's own scoping): (a) dispatch all `probeCount` workgroups every frame but skip shading for probes outside this frame's active subset via a frame-index push constant (`probeIndex % amortizationFactor == currentFrameSlot`), or (b) dispatch only `probeCount / amortizationFactor` workgroups with an index-remapping table. (a) is chosen: it needs no CPU-side dispatch-dimension changes (still a build-time constant, matching the existing precedent's own stated rationale for why dispatch dims are static here), no remap buffer, and the per-invocation cost of an idle workgroup that exits before `TraceWorld` is negligible relative to the traversal it skips — the entire point of amortization is skipping the ray-cast, not the workgroup launch overhead. (b) is noted as a fallback if M2's live bench shows (a)'s dispatch-side overhead is non-trivial (unlikely given the pass is already dominated by ray-traversal cost, not launch count, per Inc4's own ~20-24ms/512-probe measurement implying ~40-47µs/probe average).

**Existing plumbing to extend, not replace.** `probeUpdatePushConstantGatherer` already exists (wired in Inc4 M4's KI-029 fix, binding `instanceCount` — `BuildRenderGraph.cpp` search "probeUpdatePushConstantGatherer") — a frame-index field is an ADDITIVE field on the same push-constant struct, mirroring how `instanceCount` itself was added, not a new gatherer. `ProbeGridConfigNode.cpp` already has an established "CPU default + env-var override" pattern for `raysPerProbe` (`VIXEN_PROBE_RAYS_PER_PROBE`, Inc4 M6) and `probeGridEnabled` — the new `amortizationFactor` field (and any tuned default changes to `raysPerProbe`/`countX/Y/Z`) follow the exact same node/field/env-var shape, zero new infrastructure pattern.

**Measurement infrastructure already exists and is directly reusable.** Inc4 M6/M7 built: the CPU FrameTimer A/B harness (`VIXEN_PROBE_GRID_CONFIG_ENABLED` lever), the `VIXEN_PROBE_RAYS_PER_PROBE` bench override, `VIXEN_DDGI_LEAK_GATE_DEMO` (leak-test scene, unaffected by amortization since it targets specific named probes), `VIXEN_DDGI_EDIT_LOOP_DEMO` (convergence gate — the ONE gate genuinely at risk from amortization, since a probe now only updates every `amortizationFactor`-th frame, directly extending its own effective convergence window; must be re-derived, not assumed unaffected), `VIXEN_M5_SHADE_GATE_DEMO` (production gather, unaffected — gather reads whatever's currently in the atlas regardless of update cadence). No new gate scenes are needed; the EXISTING gates need to be re-run with amortization on, and the edit-loop gate's own closed-form EWMA math (already independently verified by Inc4 M6's validator) needs re-deriving for the amortized cadence.

**KI-028's fix is a prerequisite fact, not new context.** Inc4 M4 found and fixed a real M3 bug (KI-029 post-renumber): `probeUpdatePushConstantGatherer` never wired `instanceCount`, so every probe ray silently missed. This is already fixed and Opus-validated on main — noted here only because Inc5's own push-constant addition touches the SAME gatherer, so the M4 fix's own established wiring pattern (mirror `DirectLighting`'s push-constant gatherer wiring) is the direct precedent to follow for adding the new frame-index field, not something to re-discover.

## Tasks

### Task 1 (M1) — Amortized update schedule, byte-identical escape hatch
- Add `amortizationFactor` (uint, default 1) to `ProbeGridConfig` `[GpuStruct]` schema (`codegen/config-schemas/ProbeGridConfig.cs`), regenerate C++/GLSL, extend the existing 3/3-passing drift-guard test.
- Add a frame-index field to the existing `probeUpdatePushConstantGatherer`'s push-constant struct (additive, mirrors KI-029's own `instanceCount` wiring precedent) — CPU increments a frame counter each tick (or reuses an existing frame-counter source if one already exists on the app/graph — check `AccumulationConfigNode`'s own frame-counter precedent, Inc2, before adding a new one).
- `ProbeUpdate.comp`: after the existing `probeIndex >= probeCount` early-out, add `if (amortizationFactor > 1u && (probeIndex % amortizationFactor) != (frameIndex % amortizationFactor)) return;` — a THIRD early-out in the same family as the existing two, zero changes to any shading/atlas-write logic below it.
- `ProbeGridConfigNode.cpp`: `VIXEN_DDGI_AMORTIZATION_FACTOR=<n>` env override, mirroring `VIXEN_PROBE_RAYS_PER_PROBE`'s exact established shape (Inc4 M6).
- **Gate:** `amortizationFactor=1` byte-identical to Inc4's shipped behavior (every probe updates every frame, matches today exactly — this is the critical regression check, since `amortizationFactor=1`'s modulo condition `(probeIndex % 1) != (frameIndex % 1)` must be `0 != 0` i.e. always false, i.e. never skips — verify this arithmetic identity explicitly, don't just assume the formula degenerates correctly). `amortizationFactor>1` on a live render: probes visibly still light the scene (no probe permanently dark), each individual probe's own update cadence visibly drops (a debug counter or the existing DIAG hit-count field re-purposed to confirm a given probeIndex only writes 1-in-N ticks). No new VUID types; all 6 established Inc4 gates re-run clean.

### Task 2 (M2) — Convergence re-derivation + joint bench
- Re-run Inc4's own `VIXEN_DDGI_EDIT_LOOP_DEMO` gate with `amortizationFactor>1` (e.g. 8): the closed-form EWMA math Inc4 M6's validator independently derived (`T·(1-(1-rate)^N)` for N ticks) must be re-derived for "N EFFECTIVE update ticks over N×amortizationFactor WALL ticks" — confirm live-gate numbers match this adjusted closed form, not the original. This is the ONE place amortization can silently break something already gate-verified; treat it with the same rigor Inc4 M6 applied to the original derivation, not a rubber-stamp "it still sort of converges."
- Joint real-GPU bench: CPU FrameTimer A/B across a small matrix of (raysPerProbe × amortizationFactor) combinations — reuse Inc4 M6's exact bench methodology (2 runs/point, steady-state windows, `VIXEN_DDGI_LEAK_GATE_DEMO` scene for comparability against Inc4's own recorded numbers). Report a real table, not an extrapolation — confirm amortization's cost scaling is genuinely ~linear in `1/amortizationFactor` (expected, since it's a pure work-reduction lever) rather than assuming it without measuring.
- **Gate:** live-gated convergence math matches the adjusted closed form within the same tolerance Inc4 M6 achieved for the unadjusted case; bench table captured with the same signal-quality honesty Inc4 M7's own artifact used (report stdev/signal, not just means).

### Task 3 (M3) — Tune shipped defaults, full regression

## Self-Review

- **Why amortization + tuning together, not amortization alone?** M6's own bench (Inc4) showed raysPerProbe scales the cost near-linearly on its own — a combined lever (fewer active probes/frame AND fewer rays/probe) compounds two independent multiplicative reductions rather than relying on one lever to close a ~24ms gap alone, which would need an aggressive amortizationFactor that risks the convergence-window tradeoff M2 is scoped to catch.
- **Why is M2 (convergence re-derivation) its own milestone, not folded into M1?** Amortization's mechanical shader change (M1) is low-risk (an additional early-out in an already-early-out-heavy function) but its BEHAVIORAL consequence (slower per-probe update cadence) is the one place this increment could silently regress something Inc4 already gate-verified (edit-loop convergence). Isolating it as its own live-gated milestone, before any default-tuning commits to a specific amortizationFactor, mirrors this program's own standing discipline (Inc4 M1's own "gate the risky architectural question before building on top of it" pattern).
- **Why NOT bundle HW-RT acceleration or multi-queue into this increment?** Per the direction doc's own explicit sequencing recommendation — this increment is deliberately the cheap, universal, no-new-architecture fix that helps every machine (RT-capable or not) and should ship independently before either of the larger, riskier axes, giving them a smaller/better-tuned baseline to build on rather than accelerating an untuned worst case.
- **Deliberate non-scope:** any change to probe-update's shading correctness (leak rejection formula, hysteresis blend direction, light-tree sampling) — all already Opus-validated in Inc4, out of scope for re-litigation; the M5 shade-pass gather itself (reads whatever's in the atlas, unaffected by how often it's refreshed); HW-RT and multi-queue (separate future increments per the direction doc); **mip/tier-derived non-uniform probe density** (user-flagged 2026-07-13, deliberately deferred to Inc6 — see `Sampled-Lighting-Inc6-Scoping-Note-2026-07.md`). Inc5's amortization/tuning levers are PARAMETRIC (same uniform grid, less work per frame); mip-derived density is STRUCTURAL (non-uniform grid addressing keyed to the octree's own LOD/tier structure, new atlas packing, new gather-side tier lookup) — a materially bigger, slower, higher-risk change that deserves its own increment rather than inflating Inc5's deliberately small/fast scope. Sequencing them in this order also means Inc6 inherits Inc5's already-tuned per-probe cost (fewer rays, amortized cadence) as its OWN starting baseline, rather than the two changes being entangled in one gate.
- **Biggest risk:** the edit-loop convergence gate (M2) — if amortization's effective convergence window becomes noticeably worse (not just mathematically slower, but VISUALLY sluggish/stale-looking on a live edit), that's a real UX tradeoff the design doc's own "edit-loop responsiveness" gate requirement was written to catch, and would need to be weighed explicitly (accept a slower edit-response in exchange for frame-budget headroom, or dial back amortizationFactor) rather than silently accepted because the math technically still converges.
