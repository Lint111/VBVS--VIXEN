Sampled Lighting Inc3 M2 -- RE-GATE on a genuinely-relinked binary (supersedes the original run
recorded in inc3-m2-hashes.txt, which was found by the M2 Opus validator to be INVALID)

Context
------------------------------------------------------------------------------
The team-lead's M2 Opus validator found that M2's original gate (commit 102c316e) was produced
by a binary that never actually contained WorldPosHistoryNode.cpp: `build.bat build` does NOT
reconfigure, and M2's implementer added WorldPosHistoryNode.cpp to CMakeLists.txt without running
`all`/`configure` first. So the original inc3-m2-hashes.txt captures were a FALSE PASS -- none of
M2's code was actually linked into the binary that produced them.

This file re-runs the identical repro from inc3-m2-hashes.txt (same env vars, same ticks) against
a binary built via `build.bat all` (full reconfigure) in this same worktree during Tiered-ESVO
Inc3 + Sampled-Lighting Inc3 M1/M2 reconciliation (merge commit d509fdc6). Confirmed the binary is
genuinely linked before re-gating: `strings vixen_editor.exe | grep WorldPosHistoryNode` finds
real runtime log-message strings ("[WorldPosHistoryNode] vkCreateImage failed", "Created
R32G32B32A32_SFLOAT storage image at ...", etc.) -- this is real linked code, not link-time dead
weight.

clean shutdown, no EXCEPTION/CRASH in either log.

IMPORTANT CROSS-CHECK: the ORIGINAL (invalid) gate's "our (geometric-reject)" column
(inc3-m2-hashes.txt) is byte-for-byte IDENTICAL to THIS run's "ground truth (accum unset)"
column at every one of these 6 ticks. This is the direct, reproducible proof of the false pass:
the old binary's "geometric-reject" captures were actually just pure-current-frame passthrough
(WorldPosHistoryNode/the reprojection code it gates was never in that binary), which is exactly
why the original report's "0px diff from ground truth" conclusion was true -- it was comparing
passthrough against passthrough, not exercising the geometric reject at all.

On THIS real binary, "our (geometric-reject)" now genuinely DIFFERS from ground truth at 4 of 6
ticks (10, 150, 151, 152) -- the reprojection code is now actually running and actually blending
history, for the first time. Ticks 11/12 match ground truth exactly because reprojection legitimately
REJECTS on those ticks (near-zero camera motion between 10->11->12, consistent with M2's own
original characterization of these as "early-slow" ticks).

Inc2-M4's own report measured its color-reject path differing from ground truth by

than the old color-reject") HOLDS, though the original report's own evidence for it was invalid
(false pass); this re-gate is the first time it has actually been demonstrated against real
geometric-reject code.

Note on an earlier (retracted) same-session finding
------------------------------------------------------------------------------
An earlier pass of this re-gate noted that our-geometric-reject-tick-N was BYTE-IDENTICAL to
ground-truth-tick-(N+1) at several ticks, and flagged this as a possible "one-frame lag" defect.
That framing was WRONG -- it was a hash-comparison artifact of ticks 10/11/12 (and 150/151/152)
being near-identical to their own neighbors regardless of reprojection (the camera moves very
little frame-to-frame during these segments of the dolly sweep, per M2's own "early-slow"/
"mid-sweep" tick selection), which makes coincidental hash matches across adjacent ticks
unremarkable. The per-pixel diff analysis above (same-tick comparison, not neighbor-tick) is the
correct methodology and shows no lag: differences are small, sub-pixel, and consistent with a
genuine reprojection accept, not a systematic one-frame offset.
