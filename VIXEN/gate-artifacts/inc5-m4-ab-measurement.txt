METHOD
------
Same CPU FrameTimer A/B substitute as every prior increment's own measurement (Inc1/
Inc2/Inc3 M5-M7, Inc4 M6/M7) -- KI-019 (GPUQueryManager's isolated-dispatch timing) is
STILL open, not re-investigated here. VulkanApplicationBase's CPU-side FrameTimer,
logging avg/p99 wall-clock frame time every 120 frames. Full-frame delta (CPU submit +
GPU work + present/vsync), not an isolated GPU dispatch -- same caveat as every prior
increment's own measurement.

Scene: VIXEN_DDGI_LEAK_GATE_DEMO=1 for ALL THREE configs (same scene M4/M6/M7's own
DDGI cost measurements used), VIXEN_EXIT_AFTER_FRAMES=1500, 1920x1080 -- identical
scene/resolution/frame-count to Inc4 M7's own bench, for direct comparability.

THREE CONFIGS (the milestone's own brief):
  f8  = tuned shipped default, amortizationFactor=8, no env override
        (VIXEN_PROBE_GRID_CONFIG_ENABLED=1, no VIXEN_DDGI_AMORTIZATION_FACTOR set)
  f1  = Inc4's original shipped defaults, reproduced via the escape-hatch override
        (VIXEN_PROBE_GRID_CONFIG_ENABLED=1, VIXEN_DDGI_AMORTIZATION_FACTOR=1)
  off = fully disabled (VIXEN_PROBE_GRID_CONFIG_ENABLED=0)

Each config run 3 TIMES (not 2) -- the standing Inc2 M5 lesson taken seriously per
this milestone's own explicit instruction, because the FIRST two-runs-per-config pass
(see below) showed variance comparable to some of the deltas of interest, so a third
run was added before treating any number as final. 1500/120=12 windows/run, window 1
(frames 0-120) discarded as pipeline/shader warm-up, 11 stable windows/run, 33 pooled
windows/config. Raw logs: gate-artifacts (this dir is where the source-of-truth
numbers below are extracted from; per-window raw logs kept in the worktree's scratch
area, reproducible via the env vars above -- this file's numbers are the authoritative
record, matching every prior increment's own convention).

    delta = +1.911 ms/frame, signal = delta / avg-pooled-stdev = 1.911/1.544 = 1.24
    Per-run-pair direction check: f1_run1(61.530) > f8_run1(55.713) [+5.82ms];
    f1_run2(60.171) < f8_run2(59.516)? NO -- f1_run2 > f8_run2 by +0.66ms;
    f1_run3(60.033) < f8_run3(60.771) -- f1_run3 is LOWER than f8_run3 by -0.74ms.
    Direction is NOT unanimous across all 3 pairings (2 of 3 show f1>f8 as expected,

    re-measurement (which found F=8 cheaper in every one of 4 pairings) -- this
    session's own noise floor (run-to-run drift up to ~5ms on f8 alone, see f8_run1
    vs f8_run3: 55.7 vs 60.8, a ~5.1ms drift with NO config change at all) is

  f8 - off (tuned DDGI's absolute cost vs "disabled"):
    delta = -2.890 ms/frame (f8 is CHEAPER than "disabled" in this pooled comparison),

  f1 - off (Inc4-original DDGI cost vs "disabled", the same comparison Inc4 M7 made):
    delta = -0.978 ms/frame, signal = -0.47. Also negative/near-zero, for the same

    This session has materially more ambient noise than M7's own session did.

INTERPRETATION -- stated plainly, per this program's own honesty discipline
------------------------------------------------------------------------------
This session's own measurement is NOISY and does NOT produce a clean, reportable
absolute-cost or precise-magnitude number for either "DDGI's total cost" or
"amortization's exact savings." The "off" baseline's own noise floor (stdev
2.1-2.4ms/run) and its already-known non-zero-cost behavior (per-workgroup early-out,
not pass removal, M2's finding) make it unusable as a clean reference point in THIS
session. The f1-vs-f8 amortization comparison shows the expected direction in 2 of 3
run-pairings but not the third, with a pooled signal (1.24) well below what this
program's own established quality bar treats as clean (Inc4 M7's own 19.3, or even
Inc3 M7's weaker 1.56) -- this is WEAKER evidence than M2's own interleaved
re-measurement, which is why M2's interleaved result (F=8 unanimously cheaper in 4/4
pairings) remains the load-bearing evidence for the amortization win's DIRECTION, not
this session's own pooled number. Likely cause: real ambient machine load during this
particular bench session (consistent with the wide run-to-run drift on EVERY config,
including "off" which has no amortization-related code path to vary at all) -- the
same category of noise M2's own artifact and Inc3 M7's own artifact both already
identified and named, not a new or surprising phenomenon.

WHAT THIS MEASUREMENT DOES AND DOES NOT ESTABLISH
------------------------------------------------------
DOES establish (consistent with, not contradicting, every prior gate this increment
has already run): amortization at F=8 does not break anything, the escape hatch
(F=1 override) still reproduces Inc4-original behavior, and "disabled" still exhibits
its already-known non-zero-cost quirk. DOES NOT establish: a clean new absolute
magnitude number for the amortization win or DDGI's total cost, beyond what M2's own
already-reported, already-caveated finding says (F=8 unanimously cheaper than F=1 in
M2's own quieter interleaved re-measurement; exact magnitude explicitly flagged by M2
as not yet precision-tunable). This session's own numbers do not raise new doubt about
M2's direction finding (2 of 3 pairings here still agree with it) but they also do not
strengthen it beyond what M2 already established -- if anything, they underscore how
sensitive this class of measurement is to ambient session load, reinforcing rather
than undermining M2's own explicit caveat about magnitude precision.

HEADLINE, STATED HONESTLY (not softened, not oversold)
----------------------------------------------------------
Inc5 banks a REAL, CONFIRMED-DIRECTION cost reduction from amortization (established
by M2's own cleaner interleaved re-measurement: F=8 unanimously cheaper than F=1 in
4/4 pairings there) with the MAGNITUDE still not precisely quantified (M2's own
caveat, and this session's own noisier re-check does not resolve it either way).
raysPerProbe and grid density were deliberately left unchanged (M3, no trustworthy
tuning data existed this session for either). This means Inc5 does NOT fully resolve
Inc4's own "shipped defaults don't fit the 60fps budget" finding (`inc4-m7-ddgi-cost.txt`:
~24.1ms/frame alone, exceeding the entire 16.6ms budget) -- it is a real, banked,
confirmed-direction improvement, NOT a fix that closes the gap. The frame-budget
problem Inc4 identified is IMPROVED (a real reduction lever now exists and defaults to
ON), not RESOLVED (DDGI's probe-update cost at the shipped default still has not been
shown to fit inside a 60fps budget, and this session's own attempt to produce a clean
absolute number for it was inconclusive due to session noise, same as some of this
program's prior sessions).
