Sampled Lighting Inc3 M5 -- gate verification (spatial reuse, 2-dispatch split)

Scope
------------------------------------------------------------------------------
M5 splits DirectLighting.comp into two dispatches: DirectLighting.comp (RIS +
temporal reservoir reuse only, pure buffer producer -- no image writes) and
SpatialReuseShade.comp (neighbor reservoir combine via the SAME MIS
balance-heuristic primitive M4 built, ReservoirCombine.glsl's
reservoirCombine, shared by both dispatches -- then final shade + the
accumulation/debug-mode seam moved verbatim from the old single-dispatch
shader). The genuine cross-dispatch same-frame reservoir hazard (Dispatch 1
writes reservoirBufferA/B this frame, Dispatch 2 reads them the SAME frame)
is declared as a real GPU hazard via the array-hazard mechanism below, not
hand-waved.

Architecture redirect (user-directed, mid-milestone)
------------------------------------------------------------------------------
The initial implementation added 3 more fixed named slots to
ComputeStageNodeConfig (BUFFER_WRITE_B/READ_C/READ_D) to carry the new
buffers -- flagged by the user as ComputeStageNodeConfig accumulating a
special-case slot per feature, violating the pure-graph philosophy. Redirected
to a generic array mechanism mirroring the existing
DescriptorResourceGathererNode/PushConstantGathererNode pattern:

  - BufferSyncGathererNode (NEW): a VariadicTypedNode gathering N VkBuffer
    inputs into one std::vector<VkBuffer> OUTPUT_SLOT, exactly like the
    existing gatherers gather descriptors/push-constant fields.
  - ComputeStageNodeConfig: BUFFER_WRITE/BUFFER_READ_A/BUFFER_READ_B (3 fixed
    slots) collapsed into BUFFER_WRITE_ARRAY/BUFFER_READ_ARRAY (2 generic
    array slots).

This surfaced a genuine architectural blocker: ResourceAccessTracker keys
hazard tracking by ONE Resource* per static slot, and FrameSyncScheduler bakes
an edge per ADJACENT-groupId pair on a shared Resource*'s access timeline --
collapsing 2 independent producers (e.g. aStage writes bufA, bStage writes
bufB) onto one shared array Resource* would bake a SPURIOUS aStage->bStage
edge instead of 2 independent producer->consumer edges. Resolved via full
tracker surgery (user-directed, not scope-limited): Resource gained an opt-in
hazardConstituents_ field (a per-array-wrapper list of the TRUE underlying
Resource*s it was gathered from); ResourceAccessTracker::AddNode expands any
resource carrying constituents into N independent RecordAccess calls against
each constituent's OWN identity, letting FrameSyncScheduler (UNCHANGED) bake N
genuinely independent edges. Proven via 2 new unit tests
(FrameSyncArrayHazard suite, test_frame_sync_scheduler.cpp) and the existing
VIXEN_FANIN_DEMO 2-independent-producer proof, migrated onto the new
mechanism with zero regression.

GOTCHA found this milestone (environmental, not a code defect): the
RenderGraph's persistent pipeline/descriptor-layout cache
(binaries/cache/{devices,global}) survived across a slot-index renumbering
(ComputeStageNodeConfig's TIMELINE_SEMAPHORE_IN/TIMELINE_FRAME_BASE_IN/
IMAGE_WRITE all shifted by -1) and served STALE cached pipeline/descriptor
state keyed by binding index rather than by content hash -- this produced a
small but genuine pixel diff (a 32x32 block, max channel delta 32, at the
render target's edge) that looked exactly like a real code regression until
isolated via a from-scratch worktree A/B (git worktree add at each commit,
independently rebuilt, byte-identity re-checked at each step) plus a
ccache-cold rebuild (ruled out ccache) -- the actual fix was `rm -rf
binaries/cache` (a PARTIAL clear of only cache/devices + cache/global
subfolders was NOT sufficient; the full directory needed removing). Filed as
a friction point: any future slot-index renumbering on a config type with a
persistent binaries/cache/ entry should clear that cache as part of the
change, not rely on the cache's own invalidation.

New spatial-combine CPU-mirror identities (test_reservoir_mirror.cpp)
------------------------------------------------------------------------------
Both reuse Reservoir::Combine -- the SAME primitive as M4's temporal combine
(no separate "spatial" math exists; spatial reuse is just "another reservoir
stream to fold in", per the plan's shared-primitive mandate).
  - SpatialCombineReducesAcrossPixelVariance: chaining 4 neighbor Combine
    calls (mirrors ReservoirConfig::spatialCount default) reduces per-pixel
    estimator variance vs a single un-combined reservoir over 4000 runs, and
    both estimators stay within 5% of the true candidate-power sum (variance
    reduction must not shift the mean).
  - ChainedSpatialCombineStaysUnbiasedOverManyRuns: 20,000 runs of a
    4-neighbor chained combine converge to the true sum within 2% relative
    error (same tolerance/methodology as M4's own TemporalCombineStays
    UnbiasedOverManyRuns).

GPU wiring verification (live, real render loop)
------------------------------------------------------------------------------
Both shaders (DirectLighting.comp, SpatialReuseShade.comp) compiled
successfully from source at runtime. DirectLighting.comp is now a pure buffer
producer (rgba8 readonly outputImage for the accumulation-history seam only,
no writeonly image), reads HitRecord/LightingConfig/ShadowConfig/
AccumulationConfig/PrevCameraConfig/worldPosHistoryImage(readonly)/

Variance reduction vs M4 (spatial reuse's own contribution)
------------------------------------------------------------------------------
Gated primarily via the CPU-mirror SpatialCombineReducesAcrossPixelVariance
test above (GPU-side: no dedicated post-spatial-combine numeric readback
exists yet in VulkanGraphApplication.cpp to directly compare rendered-pixel
variance pre/post spatial reuse on real GPU output -- VIXEN_RESERVOIR_
SPATIAL_COUNT=0 vs the default 4 both feed VIXEN_RESTIR_GATE_DEMO's existing
readback identically, since that readback samples DirectLightingNode's
buffer BEFORE spatial reuse runs). The CPU-mirror identity is the mandated
red-green precondition per the plan (same discipline as M4's own reservoir
math); a future milestone adding a post-spatial-combine GPU readback could
close a direct on-GPU variance comparison, but is not required for this
milestone's gate (spatial reuse's math is proven correct+variance-reducing
at the CPU-mirror level, and proven non-regressing+stable live on GPU).
