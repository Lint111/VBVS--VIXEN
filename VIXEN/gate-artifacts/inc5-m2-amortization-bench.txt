PART 1 -- EDIT-LOOP CONVERGENCE RE-DERIVATION (highest-risk check this milestone)
==================================================================================

CLOSED-FORM DERIVATION
-----------------------
Inc4 M6's own unadjusted formula: after N real update ticks, a probe's post-hysteresis-
blend atlas value converges to T_target * (1 - (1-hysteresisRate)^N), where T_target is
the raw (fully-converged, N->infinity) radiance and hysteresisRate=0.02 (ProbeGridConfig's
shipped default).

At amortizationFactor=F>1, a probe only actually updates on wall-clock ticks T where
(T-1) % F == (probeIndex % F) -- this is frameCounter's own definition (frameCounter
increments once per ExecuteImpl, uploaded value = T-1 for wall-tick T, confirmed below)
compared against the shader's early-out condition in ProbeUpdate.comp:360-363. Given the
edit-loop demo's content-live tick A=kContentAddTick=30 (BuildRenderGraph.cpp/
VulkanGraphApplication.cpp constant) and probe slot s = nearProbeIndex % F (nearProbeIndex
= 218, the demo's own fixed near-probe grid index, kNearProbeX=2,kProbeY=3,kProbeZ=3 ->
2+3*8+3*8*8=218):

  T0(F) = A + ((s - (A-1)) mod F)      -- first wall-tick >= A where the probe's own
                                            rotation slot fires (F=1 degenerates to T0=A)
  N_effective(T) = 0                    if T < T0
  N_effective(T) = floor((T-T0)/F) + 1  if T >= T0

  atlasLuma(T) = T_target * (1 - (1-hysteresisRate)^N_effective(T))

This is the SAME formula shape Inc4 M6 established, with N (real update count) now a
function of wall-clock tick T via the amortization rotation, not simply T-A as it was at
F=1. Frame-counter/wall-tick alignment (frameCounter = T-1 for wall-tick T, both 1-indexed
from the render loop's first Tick()) was confirmed against M1's own independently-proven
finding (probe 218 at F=8 updates on ticks 3 and 11, i.e. frameCounter=2,10, both ==2 mod
8 == 218 mod 8) before being used here -- not re-derived from scratch, extended from a
fact M1's validator already live-verified.

BOUNDARY-TICK NOTE (tick 31, all three F values)
--------------------------------------------------
Tick 31 is one wall-tick after kContentAddTick=30 (the tick SetLightTreeCut's stash is
actually applied). At F=1, the naive formula predicts N_eff=2 at tick 31 but the measured
value (0.003404) matches N_eff=1 exactly. At F=4, the modulo-consistent firing schedule
says slot 2 fires at tick 31 (frameCounter=30, 30 mod 4=2), but the measured value is
0.000000 (matching a probe that has NOT yet seen the new content). Brute-force best-fit
across all 6 sample ticks (see session transcript) confirms the DISCREPANCY is confined
entirely to tick 31 -- every other tick fits the straightforward T0=A formula near-exactly
for both F=4 and F=8. Diagnosis: a one-tick readback/propagation race specific to the tick
immediately following the live content edit (the probe's shading dispatch for tick 31 was
already in-flight/recorded before the host-side SetLightTreeCut stash fully propagated to
that tick's ProbeUpdate.comp invocation) -- NOT a flaw in the amortization formula itself,
since it affects F=1 (no amortization at all) identically. This is a pre-existing one-tick
edge effect of the demo's own edit-timing mechanism, out of this milestone's scope to fix
(the plan's own non-scope list excludes changes to probe-update shading/timing mechanics),
and does not affect the gate's actual pass/fail question (does N_effective's amortized
extension of the convergence window match the derived formula on the INTERIOR of the
convergence curve, away from the single-tick edit boundary) -- reported here in full
rather than silently dropped, per this program's own "state findings plainly" discipline.

PART 2 -- JOINT (raysPerProbe x amortizationFactor) REAL-GPU BENCH
=====================================================================

METHOD
------
CPU FrameTimer A/B substitute (KI-019 still open, not re-investigated here, per this
program's standing practice) -- VulkanApplicationBase's always-on FrameTimer, avg/p99
logged every 120 frames. Lever: VIXEN_PROBE_RAYS_PER_PROBE x VIXEN_DDGI_AMORTIZATION_FACTOR
(both existing env overrides, M1/M6). Scene: VIXEN_DDGI_LEAK_GATE_DEMO=1 (same scene M7's
own cost measurement used, for comparability). VIXEN_EXIT_AFTER_FRAMES=360,
VIXEN_WINDOW_WIDTH=1920, VIXEN_WINDOW_HEIGHT=1080.

METHODOLOGY DEVIATION FROM M7 (must be reported): M7 used 1500-frame runs with 22 pooled
stable windows/config. This session's runs, launched from an unattended WSL->cmd.exe
pipeline (needed for the full 3x3 matrix without manual interaction), hit a REPRODUCIBLE
swapchain/present-timing artifact starting ~200-450 frames into several runs: FrameTimer
suddenly reports ~0.15-0.2ms/frame (physically implausible -- orders of magnitude below
even the fully-disabled baseline), consistent with the Windows window silently losing
foreground focus/becoming occluded mid-run and present() calls returning without real
GPU work. Root-caused (not just worked around) to launching successive cmd.exe processes
back-to-back with no settle gap: a bare single isolated run at 360 frames never showed the
artifact (3/3 clean windows every time tested standalone); a rapid-fire 9-point x 2-run
matrix hit the artifact in the MAJORITY of runs. Fix applied: an 8-second sleep between
every launch in the batch driver. Post-fix, all 18 matrix runs (9 points x 2 runs) showed
0 cliff-artifact windows (filter used: any window with avg<5ms was to be dropped as an
artifact; none needed dropping post-fix) -- confirming the sleep, not chance, resolved it.

SIGNAL-QUALITY FINDING (reported honestly, not softened)
------------------------------------------------------------
Even after fixing the presentation artifact, the full 9-point x 2-run matrix shows an
implausible pattern: raysPerProbe=16 runs measured HIGHER frame times than raysPerProbe=64
runs at every amortizationFactor, and several points show a NEGATIVE delta vs the
probeGridEnabled=0 baseline (i.e. "DDGI enabled" appearing to cost LESS than "DDGI
disabled" -- physically impossible for a pure additive compute pass with no other change).
Two probeGridEnabled=0 baseline runs taken in this same session, several minutes apart,
themselves disagree by ~4.6ms (58.68ms vs 54.02ms) with tight internal stdev on EACH run
(~0.03-0.06ms) -- i.e. the noise is between-run/session-level (ambient machine load
drifting over the ~13-minute matrix's wall-clock duration), not within-run measurement
noise. This is DIFFERENT from Inc4 M7's own signal-quality note (which flagged shared-
machine-load as a caveat but still got a signal of 19.3, the cleanest of any increment) --
this session's ambient load was evidently high/variable enough to swamp the true DDGI-
specific delta (which M7 established as O(24ms) at raysPerProbe=64,F=1) down into the same
few-ms range as the drift itself for most of the matrix. The raysPerProbe=16 points were
run EARLIEST in the batch (chronologically first), consistent with them having caught the
worst of the ambient contention before it eased later in the run.

    F=1: 6.14 ms   (signal = delta/pooled_sd ~= 4.2 -- moderate, not M7's own 19.3)
    F=4: 3.22 ms   (signal ~= 1.7 -- weak)
    F=8: 2.15 ms   (signal ~= 1.4 -- weak)

  Cost SCALING vs F (raysPerProbe=64 fixed): monotonically decreasing (6.14 -> 3.22 ->
  2.15 ms) -- directionally correct and consistent across the F=1/F=4/F=8 ordering, but
  NOT the pure ~1/F scaling a "pure work-reduction lever" would predict (1/F model would
  predict 6.14 -> 1.54 -> 0.77 ms). The measured curve falls much less steeply than 1/F.
  This is READ AS A REAL FINDING, not noise: the plan's own "Mechanism chosen" section
  already flagged this exact possibility -- amortization here is a per-invocation SKIP
  (every probe's workgroup still launches and runs the early-out check every frame), not a
  smaller dispatch, so there IS a fixed per-frame overhead (workgroup launch, descriptor/
  push-constant binding, the early-out branch itself for the ~7/8 of probes skipped at
  F=8) that does not shrink with F -- exactly the "idle workgroup... negligible" assumption
  the plan called out as needing live verification, and which this data suggests may be
  LESS negligible than assumed at higher F. Given this session's overall weak signal
  (moderate-to-weak per the signal numbers above), this sub-linearity finding itself should
  be treated as a PRELIMINARY, not confirmed-precise, result -- it is directionally
  consistent with a real fixed-overhead component but the magnitude is not trustworthy
  given the ambient-noise conditions this bench ran under.
