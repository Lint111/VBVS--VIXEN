Bug found + fixed en route: color-consistency validation
------------------------------------------------------------------------------
The FIRST version of the reprojection shipped with only bounds (on-screen) + motion-magnitude
(reprojected-texel screen-space distance <= 8px) validation, per the milestone brief's
"simpler-but-correct" option. Live-gated against the SAME dolly-in sweep and found a REAL bug:
a slowly-growing silhouette edge (camera dollying toward the body) moves by only 1-2 texels per
frame, so it always passed both checks, yet at a shrinking alpha (~1/150 deep into the sweep) the
blend was 99%+ weighted toward increasingly-stale history -- diffed against the pure-current
ground truth this showed an UNBOUNDED, growing dark "sky-colored" patch eating into the body's
silhouette as the sweep progressed (234/250000 px, max channel diff 167-183, patch color exactly
matched the shader's own sky formula at that UV -- i.e. the accumulated pixel was rendering a
frozen, several-frames-stale, too-small silhouette's sky-background instead of the newly-revealed
body surface). This IS the disocclusion/newly-revealed-geometry case the milestone brief warned
simple bounds+motion validation might miss. Root-caused (not worked around) to: no
depth/worldPos cross-check means bounds+motion-magnitude alone cannot detect "reprojects to an
on-screen, nearby texel that happens to belong to a DIFFERENT (stale, smaller-silhouette)
surface." Fixed by adding a THIRD validation term: reject the reprojected history sample if its
color differs from THIS frame's own outColor by more than 0.15 (normalized [0,1], any channel) --
a standard cheap TAA disocclusion heuristic when no motion-vector-validated depth buffer exists.
Post-fix the failure signature above (unbounded growth, exact sky-color patch) is gone; the
residual diff (documented in the ground-truth table above) is bounded, plateaus, and is
edge-color-range, not sky-color-range -- confirmed via the same pixel-patch inspection.
