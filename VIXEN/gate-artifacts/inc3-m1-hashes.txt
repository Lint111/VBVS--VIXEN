Sampled Lighting Inc3 M1 -- Separate DirectLighting pass (KI-018) -- live gate

This gate required THREE orthogonal fixes before it could even run (all found via live
verification, none caught by the prior static/compile-only checks -- see Known-Issues at
close-out). All three are pre-existing/unrelated to M1's own architecture (RenderGraph
sync-slot/BlitNode/IMAGE_WRITE/BUFFER_WRITE work), just first-exercised by this milestone's
gate:
  1. application/main/source/FrameCapture.cpp: stale `#include "Profiler/FrameCapture.h"` left
     over from the build-policy merge (9b43c376)'s Profiler-consolidation. Fix already existed
     as commit b30e08e9 on sibling branch feat/tiered-esvo-inc3 (Opus-validated there);
     cherry-picked onto this branch (HEAD 5835ef18).
  2. libraries/ShaderManagement/src/ShaderPreprocessor.cpp: `includeGuard` (an unordered_set
     tracking #include recursion) was never erased after a nested ProcessRecursive() call
     returned, so it accumulated EVERY file ever seen anywhere in the whole include tree
     instead of just the currently-active include chain -- a guarded (#ifndef) file included
     twice, non-nested, was misreported as "Circular include detected" even though the guard
     makes the second inclusion a harmless no-op in every other GLSL/C preprocessor. Surfaced
     because DirectLighting.comp (M1's new shader) legitimately includes
     Generated/LightingConfig.glsl twice non-nested (once transitively via SceneBindings.glsl
     for the struct-type-before-use requirement, once directly for its own SSBO binding
     declaration) -- a correct, intentional, documented pattern that just happened to be the
     first shader to exercise this preprocessor bug. Fixed: erase canonicalPath from
     includeGuard right after the nested call returns (covers both its success and error path).
     Added regression coverage: libraries/ShaderManagement/tests/test_shader_preprocessor.cpp
     (GuardedFileIncludedTwiceNonNestedSucceeds, TrueCircularIncludeStillDetected) -- both PASS.
  3. libraries/RenderGraph/CMakeLists.txt: RenderGraphNodes never had VIXEN_SHADER_SOURCE_DIR
     defined (only application/main/VixenApp did), so any RenderGraphNodes node compiling its
     own shader from source (e.g. SkyProjectionNode::ResolveShaderPath) fell through to
     CWD-relative fallbacks ("shaders", "../shaders") that don't resolve when vixen_editor.exe
     runs from its own binaries/ output dir. SkyProjectionNode predates M1 (Tiered-ESVO Inc1 M3,
     commit 4ae045a4) and was already unconditionally wired into the default scene graph
     pre-M1 (confirmed via git history at Inc2 tip fb5dfda4) -- this was always a latent gap,
     not introduced by M1; M1's gate is simply the first capture run exercising a real
     from-clean-build CWD where no stray shaders/ happened to resolve by coincidence. Fixed:
     added `target_compile_definitions(RenderGraphNodes PRIVATE VIXEN_SHADER_SOURCE_DIR=...)`
     mirroring application/main's identical existing definition.

All three: team-lead reviewed/verified before I applied any of them (git-history-verified for
#1 and #3, source-read-verified for #2); I did not make unilateral scope calls.

Gate 3: live syncval -- the auto-sync barrier baking (both hazard checks named in the milestone)
------------------------------------------------------------------------------
Validation layers are always-on for this Debug build (VIXEN_VULKAN_VALIDATION=1 compile
define, confirmed in the VixenApp compiler invocation) -- so Gate 1's default capture run IS
the live syncval run; log = temp/run_inc3_m1_capture_default.log (1283 lines).

(i) HitRecord read-before-write hazard: ZERO occurrences. No "SYNC-HAZARD", "read-before-write",
    or WAR-pattern message anywhere in the log. Confirms M1 decision-3's fix (BUFFER_WRITE-shaped
    INPUT_SLOT_SYNC on ComputeDispatchNodeConfig for the march's HitRecord write, consumed by
    DirectLightingNode's BUFFER_READ_A) actually baked a real cross-submit sync edge -- the march
    (vkQueueSubmit2 #1) and DirectLighting (vkQueueSubmit2 #2) are genuinely ordered.

(ii) Swapchain-image layout/WAR hazard: ZERO occurrences on the swapchain image specifically.
     Confirms M1 decisions 2 and 4 (IMAGE_WRITE slot on ComputeStageNode + WRITES_NO_IMAGE flag
     on ComputeDispatchNode) compose correctly: the march no longer touches a presentable image
     it doesn't own, DirectLighting's IMAGE_WRITE->GENERAL transition and BlitNode's final
     transition to PRESENT_SRC don't double-transition or race.

A SEPARATE, pre-existing image-layout VUID WAS observed, unrelated to the swapchain/M1's own

pipeline (test_dispatch/compute_desc_gatherer), not on the march/DirectLighting/BlitNode chain

Other findings (real, NOT M1-caused, recorded here per team-lead's close-out instruction)
------------------------------------------------------------------------------
(A) `[compute_desc_gatherer] [ERROR] [DescriptorResourceGathererNode::Execute] ERROR: Binding 21
    out of range (resourceArray_.size()=18)` -- 22 occurrences at default scale, 80 at 0.5x
    render-scale (same signature, count scales with dispatch/frame count as expected of a
    per-execute error, not a new failure mode from scaling). This node ("compute_desc_gatherer",
    BuildRenderGraph.cpp ~line 168, tagged "Phase H") backs the GENERIC demo/test compute
    pipeline ("test_dispatch"), NOT the march, DirectLighting, or BlitNode this milestone
    touches. Correlates with a VUID-vkCmdDraw-None-09600 image-layout mismatch (expects
    GENERAL, finds UNDEFINED/TRANSFER_SRC_OPTIMAL) and a VUID-vkUpdateDescriptorSets-None-03047
    (descriptor set updated while in use by a pending command buffer) on the same test pipeline.
    Byte-identical Gate 1 still passed despite this, meaning it does not touch the pixels this
    milestone's default scene actually renders -- but it IS a real, reproducible defect, most
    likely this demo pipeline's own descriptor array never grew to match the binding count as
    Inc2/Inc3 added new SSBO bindings (19-21) to the main scene graph elsewhere. Recommend a
    Known-Issue entry; NOT blocking this milestone's gate since it's provably orthogonal
    (different node, different pipeline, zero pixel impact), but flagging per team-lead's
    "record both orthogonal fixes... as separate Known-Issue candidates" instruction -- this is
    a THIRD such candidate, found rather than fixed (out of scope to fix without its own
    investigation).
(B) `[direct_lighting_push_constant_gatherer]` and `[push_constant_gatherer]` both emit "Type
    mismatch for field" ERROR lines (13 each, 26 total) -- SAME class Inc1-M1's own gate doc
    already documented as pre-existing baseline noise for the march's gatherer; DirectLighting's
    OWN new gatherer inherits the identical benign pattern (harmless per Inc1's precedent; byte-
    identical result confirms zero visual effect). Not a new finding, just confirming continuity.
(C) SdiLifecycleTest.UpdateShaderAndRegenerateSdi fails intermittently on a filesystem-mtime-
    resolution race (`timestamp1 != timestamp2` when two writes land in the same Windows FS
    mtime tick) -- pre-existing (untouched by any commit this milestone), unrelated to shaders/
    RenderGraph; not investigated further per scope.
