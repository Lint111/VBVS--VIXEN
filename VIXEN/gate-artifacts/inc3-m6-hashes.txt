Sampled Lighting Inc3 M6 -- gate verification (ReSTIR -> Inc2 accumulation -> tonemap/UI, full-stack live gate)

Scope
------------------------------------------------------------------------------
M6's task text: "Wire the noisy ReSTIR DI result through Inc2's temporal
accumulation (using M2's geometric reject) -> tonemap. This is the intended
§3 stack assembled end-to-end."

FINDING: the wiring itself was ALREADY COMPLETE by M5. SpatialReuseShade.comp
(M5's own second dispatch) already owns the accumulation seam (moved
verbatim from DirectLighting.comp, itself moved from BodyInstanceRayMarch.comp
in M1/Inc2) using worldPosHistoryImage's geometric reject (M2/KI-023), and
already owns outputImage/historyImage, feeding BlitNode -> the swapchain/UI-
composite chain. There is no separate "tonemap" operator anywhere in this
engine -- the design doc's diagram (Sampled-Lighting-Design-2026-07.md line
44, "temporal accumulation -> [denoiser, later] -> tonemap/UI") uses
"tonemap/UI" to name the EXISTING terminal UI-composite/present stage, not a
pass that needs to be built. Confirmed via grep across shaders/ and source/:
zero matches for tonemap/tonemapping/toneMap outside that one design-doc
label and one unrelated doc example file.

The actual gap M6 needed to close (self-identified from M5's own Progress
Log, which explicitly flagged it): M4/M5's equal-error-vs-brute-force gate
only ever read DirectLightingNode's PRE-spatial reservoir buffer (the
estimator BEFORE spatial reuse folds in neighbors). The spatially-combined
`current` reservoir inside SpatialReuseShade.comp exists only in shader
registers -- reservoirBufferA/B are declared readonly in that pass -- so no
GPU-visible state existed for a CPU readback to verify unbiasedness survived
spatial combine + accumulation. M5's own Self-Review: "a future milestone
adding a post-spatial-combine GPU readback could close a direct on-GPU
variance comparison... not required for [M5]'s gate."

What M6 built
------------------------------------------------------------------------------
- New debug-only SSBO (binding 27, node name `spatial_reservoir_debug_buffer`,
  ReservoirRecord/16B-per-pixel layout -- reuses the exact same generated
  struct as reservoirBufferA/B, no new type). Same extent-follow sizing
  pattern (PARAM_BYTES_PER_PIXEL=16, VULKAN_DEVICE_IN/SWAPCHAIN_INFO wired to
  compute_render_target, same as reservoirBufferA/B).
- SpatialReuseShade.comp writes its spatially-combined `current` reservoir
  into this buffer immediately after the neighbor-combine loop, for every
  pixel that enters the `reservoirEnabled && anyHitRT` block (same addressing
  as reservoirBufferA/B's own reservoirIdx = hitRecordIdx).
- Single writer (SpatialReuseNode), zero GPU readers -- Execute-only wiring,
  no new hazard class (the CPU readback happens host-side after
  vkDeviceWaitIdle, same precedent as the existing reservoirBufferA/B gate
  readback).
- VulkanGraphApplication.cpp: a second, independent readback block
  (RestirGateDemoM6PostSpatial) at the SAME tick-60 window as the existing
  M4/M5 block, computing the identical equal-error-vs-brute-force identity
  now against the post-spatial-combine buffer -- does not replace or modify
  the existing M4/M5 measurement, both print in the same run.
