## B6: any-hit recipe march

### What changed

`traceUberRecipeBody` (`VIXEN/shaders/SdfRecipes.glsl`) is the hand-written sphere-march every
recipe ray uses; only the field it calls (`evalRecipeField`) is generated by the kernel's recipe
GPU service. The shadow wave (`ShadowVisibilityWave.comp`) and `TraceWorldShadowImpl`
(`TraceWorld.glsl`) are hand-written passes too, so B6 is a hand edit and **the kernel is
unchanged** (no generated pass or generator is involved; the field text is identical).

- `traceUberRecipeBodyImpl(..., bool occlusionOnly, ...)` holds the march. With `occlusionOnly` the
  step sequence, the refinement bracket and `hitT` are the same instructions as before; only the
  six-evaluation central-difference gradient and the material evaluation at the certified hit are
  skipped. Two forms: `traceUberRecipeBody` (nearest hit: camera and probe rays) and
  `traceUberRecipeBodyAnyHit` (visibility rays).
- Callers: `TraceWorldShadowImpl` (through `traceRecipeChunks`, which takes the flag) and the
  ray-query any-hit twin `traverseRayQueryWorldAnyHit` (`RayQueryTraversal.glsl`). Both read only
  hit and distance. The shadow loop no longer transforms the normal it never read.
- The global `g_recipeProvenStepOnly` is deleted: it was `true` only around exactly these two
  any-hit calls, so the parameter carries the same relaxed-step rule.
- `g_lastRecipeMaterialId` is read only after nearest-hit traces, never after a shadow trace.
- CPU parity: `TraceWorldShadowMirror` (`test_traceworld_mirror.cpp`) models occluders abstractly
  and has no recipe march or gradient; the CPU march oracles of the bucketed-dispatch tests mirror
  the primary march, which is unchanged. No CPU face to change.

### Detector

`opus-rt6-evidence/speckle/speckle.py` (measurement-only, evidence folder, not in a repo): a pixel
whose luminance differs from all 8 neighbours by more than 12 levels in the same direction, the 8
neighbours agreeing within 12, and (strict form) the 16 pixels of the 5x5 ring agreeing too, so
stair-step corners of silhouettes and shadow boundaries are not counted. Run over the GlyphSdf set
(20), RTL pair and look-dev 16: **29 speckles on the reference set.**

Classification by probe (shader-source overrides of the same binary, shared GPU runs):
- **shadow-caused** = present in the stock capture and absent with shadows disabled
  (`TraceWorldShadowImpl` returns "lit", probe D): latin-embossed 4, qps-rtl-embossed 1.
- the rest persist with shadows disabled, so they are not shadow speckle.

### Cause (shadow-caused class)

The shadow ray of each speckle pixel, a plaque pixel inside the cast shadow of an embossed glyph,
hits the glyph's own wall between **0.1 and 1 mm** along the ray. `TraceWorldShadowImpl` rejected
every recipe hit closer than a fixed `kProceduralShadowTMin = 1e-3` world metres ("do not treat the
origin itself as an occluder", commit `9492f3c98`), and because plaque and glyph rows are **one
instance**, that rejection dropped the whole instance: the pixel read lit inside the shadow. Where
the hit lands relative to 1 mm varies pixel by pixel along the glyph wall, so the failures are
isolated pixels, and they move when bounds change the step sequence (the R892.7 package observation).

Probe evidence (latin-embossed, `speckle-probe*.log`, run dirs `C:\vixen-native\rt6-scratch\sp*`):

| Probe | Change | Result |
|---|---|---|
| A | count any hit below 1 mm as occluder | 4 of 4 shadow speckles gone, but plaque-rim acne appears (a 1 px dark line, 50 px > 8) |
| B | count exhausted marches as occluder | byte-identical to stock: exhaustion not involved |
| C | march out of the start surface (no hit before one outside sample) | byte-identical: the first sample is never inside |
| E1/E2/E3 | count hits in [0,1e-6] / (1e-6,1e-4] / (1e-4,1e-3] world | E1 = the rim acne only; E2 = no change; **E3 = exactly the 5 speckle pixels, nothing else > 8** |
| G1/G2 | E3 restricted to hits certified by the cone/bracket refinement / by `d <= EPS_MIN` | **G1 = E3**, G2 = stock |
| I (the fix) | C's start-surface rule + no world-distance guard for registry recipes | = E3 on latin-embossed; qps-rtl-embossed speckle gone; carved variants and RTL pair byte-identical |

### Fix (`11b45cde1`)

- `traceUberRecipeBodyImpl` (occlusionOnly only): until one sample is outside (`d > EPS_MIN`) the
  field the ray reads is the surface it starts on, so it marches out of it (`t += max(-d, max(4
  EPS_MIN, t))`) instead of certifying a hit at the origin. This is the start-surface case the
  1 mm guard was written for, now handled where it happens.
- `TraceWorldShadowImpl`: a registry recipe's hit is accepted from `tmin` (no world-distance
  guard); the march starts at `tmin` instead of filtering hits before it afterwards, so a hit
  before `tmin` no longer discards the instance. Legacy analytic bodies (recipe 0/1) keep the guard.
- Affected native GPU CTest on `11b45cde1`: **106/106 passed**, no device loss, 992 s to the last capture (`gpu-affected-1b.log`). No test asserts the changed pixels (the look-dev references are hash lists the owner signs off).
- Camera and probe rays (nearest hit) unchanged: RTL pair 1080p stays `8e83e9ac...` (B5 `new/`),
  HUD 3 unchanged.

### Guard (`lane-rt6-guard` `10c3406fd`, one commit on `02ac526f2`)

`kTileListCapacityLog2 = 6` (one constant for the view record and the buffers) bounds each tile's list,
and so the serial sort, at 64. A tile offered more keeps an incomplete list (`StoredCount` already
capped it) and reports demand > count; the camera march then marches the bounded instance loop for
that tile (R861.1). RTL and look-dev tiles hold at most 15 candidates, so their lists are unchanged.

### Parallel scatter (`6d0f8a23d`)

Each instance gets `TileBinOps.ScatterLanes` invocations (up to 256) walking its tile rectangle in
stride; the sorted lists are unchanged when no tile overflows. `TileBinStats.occluded` ->
`occludedSlices` (unread buffer). Generator gap found: a callable in a hoisted leading guard is emitted
with its block argument unindexed (SPT `63665642c7c8`); worked around in the facade.

### TAPE_OPERANDS lane plan (R894)

The material variant (`RegistryRequiresMaterialVariant`, `UberShaderSplice.h:111`) emits each recipe's
straight-line field with `YK_RECIPE_GPU_FIELD_TAPE_OPERANDS`: operands come from
`recipeTape[recipeOperandBase + i].data[k]` (binding 53) instead of literals. Plan: (1) kernel: the
GLSL_FIELD emitter keeps literal operands in the material variant too (the material id is a literal of
the instruction, like every other operand); (2) VIXEN: drop binding 53 and `SetRecipeTape` from the
render path; the editor's live edits use the CPU recipe evaluation until the bake recompiles (R894,
R864); (3) witness: captures of material-carrying recipes byte-identical, SPIR-V without `recipeTape`.
Size M, kernel + VIXEN.

### R892.11 distance-only check

In the RTL and look-dev scenes the march, shadow and gradient call `sdfRecipe_<id>(vec3, float[6])`,
a distance-only function (no material out parameter, SPIR-V checked). The material variant (scenes with
material-carrying recipes) calls `sdfRecipe_<id>(p, params, tapeBase, out materialId)` for every
evaluation and discards the id through the 3-argument wrapper; whether the driver strips it there is
not checked. The per-channel projection (distance-only function for traversal and gradient, property
functions at hit resolution) belongs with the TAPE_OPERANDS lane and the analytic-gradient work (R892.10).
