## 4. Fix — commit `d50d282f`

Five files, all cited above. The fix targets F1/F2/F3/F4 (the real fail-silent defects) and adds
the dzn-caps clamping the brief asked for.

**Honest negotiation (F1/F2/F3).** New `VulkanDevice::NegotiatePresentQueue(VkSurfaceKHR)`
(`VulkanDevice.cpp:399-455`) queries `vkGetPhysicalDeviceSurfaceSupportKHR` per queue family and
selects a family proven to support BOTH graphics and present. On failure it names the gap — GPU
name, family count, and the split between graphics-capable and present-capable families — so
"cannot present at all" is distinguishable from "can present, but not on a graphics family".
`vkGetPhysicalDeviceSurfaceSupportKHR` is a `VK_KHR_surface` **instance-level** entry point, so it
is callable before the logical device exists; this is what makes an honest negotiation possible at
all under the existing `instance → device → window → swapchain` graph topology
(`application/main/source/graph/BuildUIGraph.cpp:35-75`).

`graphicsQueueWithPresentIndex` now starts at `kPresentQueueNotNegotiated` (`VulkanDevice.h:66-68`)
instead of being seeded from `graphicsQueueIndex`, so `HasPresentSupport()` reports false until a
real surface proved otherwise rather than being unconditionally true.

`SwapChainNode` (`SwapChainNode.cpp:106-118`) calls the negotiation with the surface it just
created and reports what actually failed; its previous message claimed a presentation check that
never ran.

**Loud failure when presentation is requested but unsupported (F4, 0ej).**
`DeviceNode.cpp:293-319`: a requested-but-unadvertised `VK_KHR_swapchain` now throws at device
creation, naming the GPU and its advertised extension count, instead of a warning that yields a
device with a null `vkCreateSwapchainKHR` discovered much later at `ui_swapchain` compile. All
other requested extensions stay best-effort exactly as before.

**dzn-caps robustness.** `VulkanSwapChain.cpp`: the requested extent is clamped into
`[minImageExtent, maxImageExtent]` (VUID-VkSwapchainCreateInfoKHR-imageExtent-01274) and the image
count into `[minImageCount, maxImageCount]` at BOTH ends (the previous code clamped only the
maximum, so a driver reporting `maxImageCount < minImageCount+1` produced a request below the
minimum). Both negotiated values are now logged. Present-mode selection already only ever chose
from the queried `presentModes` list, so **FIFO-only drivers already worked** — no change was
needed there, and none was made.

### ⛔ Lavapipe is not an execution path (owner, 2026-09-02)

Software Vulkan was **removed**, not demoted to a fallback. The harness no longer accepts a
`lavapipe` mode at all — there is no way to ask for a software run — and it refuses to produce a
software result rather than labelling one. Rationale: a frame count rendered by a CPU rasterizer
says nothing about the hardware path it would be reported against, so producing it is a liability,
not a safety net.

This follows an **existing precedent in the tree** rather than minting a new rule:
`test_recipe_glsl_numerical_parity.cpp:237` already states *"lavapipe execution is forbidden for
this task"* and gates on `IsRealGpu()` (`:257`), which accepts only `DISCRETE_GPU` /
`INTEGRATED_GPU`. The harness now uses the same predicate.

**Dozen remains the venue, because Dozen IS real hardware.** Measured on this box, dzn presents the
physical RTX 3060 through D3D12 and reports `deviceType=2 (DISCRETE_GPU)`, `driverID=23
(MESA_DOZEN)` — it passes the same `IsRealGpu()` gate a native driver does. Lavapipe reports
`deviceType=4 (CPU)`. So the hardware-only rule narrows the harness without invalidating the venue
ruling 0ep.3 targets.

### ⚠ STOP-AND-REPORT — the engine still has the software fallback the new rule forbids

Removing lavapipe from *my harness* does not remove it from the *engine*. The hole is at
`VulkanGlobalNames.h:42-54`, `VixenSelectWslGpuIcd()`:

```cpp
if (icd && icd[0] != '\0'
    && std::filesystem::exists("/dev/dxg")
    && std::getenv("VK_ICD_FILENAMES") == nullptr
    && std::filesystem::exists(icd)) { ::setenv(...); return icd; }
return nullptr;                    // <- manifest missing => loader falls through to lavapipe
```

On a WSL2 GPU host with no explicit `VK_ICD_FILENAMES`, a missing Dozen manifest makes this return
null and the binary runs on **software Vulkan with no error**. The function's own comment block
(`:27-33`) names this exactly — *"silently downgrades every WSL2 binary to a CPU rasterizer with no
error — exactly the kind of hidden fallback that hides real GPU-path bugs"* — and then implements
the fallback anyway. Under the new rule this is a live defect of the same fail-silent class as the
presentation bug this lane fixed.

**I did NOT change it, deliberately.** Making it throw is a one-line fix, but the blast radius is
outside this lane and the call is not mine:

- **~30 callers**, nearly all tests (`grep VixenSelectWslGpuIcd`, excluding the header).
- **At least five explicitly document software fallback as intended behaviour**:
  `test_editor_document_render.cpp:27` (*"falls back to lavapipe"*), `test_recipe_pool_render.cpp:14`,
  `test_procedural_recipe_render.cpp:15` (*"a real GPU is PREFERRED, with…"*),
  `test_recipe_authoring_gate.cpp:33`, `test_appflow_editor_toggle_render.cpp:7`.
- So the tree currently holds **two contradictory doctrines**: parity/numerical tests forbid
  lavapipe (`IsRealGpu` + `GTEST_SKIP`), while render-smoke tests depend on it to run at all.

Tightening the shared selector would convert those five-plus suites from passing to throwing at
`SetUp()`. That is a fleet-level decision about which suites are allowed to run on software at all
— not a lane's to make unilaterally, and exactly the "genuine fork → STOP and report" case. The
options, for whoever rules on it:

1. **Throw in `VixenSelectWslGpuIcd()`** — strongest, closes the hole everywhere; requires
   converting every software-dependent render-smoke suite to skip (not fail) when no hardware is
   present, or giving them an explicit opt-in.
2. **Add a separate `VixenRequireGpuIcd()`** that throws, leave the existing selector permissive,
   and call the strict one from application `main()`s only — closes it for shipped binaries without
   touching the test estate.
3. **Env opt-out** (`VIXEN_ALLOW_SOFTWARE_VULKAN=1`) — default strict, tests that genuinely need
   software set it explicitly, making every software run a deliberate, greppable choice.

My recommendation is **(2) then (3)**: (2) is small, has no test blast radius, and immediately
enforces the rule where it matters most — the binaries a person actually launches. (3) then cleans
up the test estate incrementally, turning each remaining software run into an explicit declaration
instead of a silent default.
