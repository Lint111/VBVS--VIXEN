## 1. The brief's premise, and what measurement shows

The brief states: *"the LOGICAL DEVICE was created without VK_KHR_swapchain … the device-extension
negotiation drops presentation silently in this environment."*

**That specific causal claim does not reproduce.** Tested by replicating the engine's exact
ordering (filtered instance → real X11 surface → engine's physical-device selection rule → filtered device
create → `vkGetDeviceProcAddr`) against the live drivers on this box.

### Measured (probe `probe5.c`, scratchpad)

Under Mesa Dozen (`VK_ICD_FILENAMES=~/.cache/vixen/wsl-vulkan/dzn_icd.json`, `DISPLAY=:0`):

```
instance extensions kept after filter: 3
   + VK_KHR_surface   + VK_KHR_get_surface_capabilities2   + VK_KHR_xlib_surface
vkCreateInstance(apiVersion 1.3) = 0 OK
vkCreateXlibSurfaceKHR = 0 OK
selected GPU 0: Microsoft Direct3D12 (NVIDIA GeForce RTX 3060 Laptop GPU)
  qf0 graphics=1 present=1
  qf1 graphics=0 present=1
device extensions kept after filter: 2
   + VK_KHR_swapchain   + VK_KHR_synchronization2
vkCreateDevice = 0 OK
vkGetDeviceProcAddr(vkCreateSwapchainKHR) = 0x7c6182410f90  RESOLVED
```

Under the default loader (lavapipe/llvmpipe), the same flow also ends `RESOLVED`.

So: dzn **does** advertise `VK_KHR_swapchain` (46 device extensions), `DeviceNode`'s filter
**does** keep it, and the proc addr **does** resolve. The null-proc-addr signature therefore has a
different cause than "negotiation dropped the extension".

## 2. What the negotiation trace DID find (real defects, 0ej-shaped)

These are genuine fail-silent / dead-capability defects on the presentation path, found while
tracing. They are the honest-negotiation gap 0ep.3 names, even though they are not the
proximate cause of the reported null proc addr.

| # | site | defect |
|---|---|---|
| F1 | `VIXEN/libraries/VulkanResources/src/VulkanDevice.cpp:387-397` | `GetGraphicsQueueHandle()` picks the FIRST graphics family and sets `graphicsQueueWithPresentIndex = i` with the comment *"Assume graphics queue supports present (verified during swapchain creation)"*. No `vkGetPhysicalDeviceSurfaceSupportKHR` call. The assumption is never actually verified later. |
| F2 | `VIXEN/libraries/VulkanResources/src/VulkanDevice.cpp:403-407` | `HasPresentSupport()` returns `graphicsQueueWithPresentIndex == graphicsQueueIndex`, which F1 makes **unconditionally true**. The predicate can never report absence — a fail-silent capability report. |
| F3 | `VIXEN/libraries/VulkanResources/src/VulkanSwapChain.cpp:259-308` | `GetGraphicsQueueWithPresentationSupport()` — the function that DOES the per-queue-family `vkGetPhysicalDeviceSurfaceSupportKHR` query correctly — has **zero callers** in the tree (verified by grep over all `.cpp`/`.h`). The correct query exists as dead code. |
| F4 | `VIXEN/libraries/RenderGraph/src/Nodes/DeviceNode.cpp:293-300` | Every requested device extension that the driver does not advertise is dropped with only `NODE_LOG_WARNING(… NOT AVAILABLE - skipping)`. There is no notion of a REQUIRED extension, so presentation can be dropped with the same severity as an optional nicety. This is the fail-silent shape 0ej forbids, even though on this box swapchain survives the filter. |
| F5 | `VIXEN/libraries/VulkanResources/src/CapabilityGraph.cpp:138-139` | The `DeviceExt:VK_KHR_swapchain` capability node is registered in the graph, but **nothing queries it** (grep: only the registration site). Presentation is not actually capability-gated despite appearing to be. |
| F6 | `VIXEN/libraries/VulkanResources/include/VulkanSwapChain.h:198` + `src/VulkanSwapChain.cpp:432,442` | `supportsScalingExtension` is default-`false` and **never assigned** anywhere. The `VkSwapchainPresentScalingCreateInfoEXT` pNext branch is therefore dead — the `VK_EXT_swapchain_maintenance1` request in `main.cpp` buys nothing at swapchain-create time. |
| F7 | `VIXEN/libraries/RenderGraph/src/Nodes/DeviceNode.cpp:19-20` | `extern std::vector<const char*> deviceExtensionNames;` re-declares as plain `extern` a global that `VulkanGlobalNames.h:15` defines as `inline`; `DeviceNode.cpp` does not include that header. **Tested and excluded as a cause** (both plain and static-archive links resolve to the same `u`-bound symbol; two-TU repro in scratchpad `odr/`), but it is a real ODR-adjacent smell. |

## 3. Environment findings (not in the brief)

- **There is no dzn ICD in the system Vulkan path.** `/usr/share/vulkan/icd.d/` holds only Mesa's
  stock ICDs; Ubuntu's `mesa-vulkan-drivers` (25.2.8) ships **no** `libvulkan_dzn.so`. Dozen is
  built from source by `VIXEN/cmake/ProvisionWslVulkan.cmake` into
  `~/.cache/vixen/wsl-vulkan/` (present on this box, built 2026-06-13) and is selected ONLY via
  `VK_ICD_FILENAMES` / the `VIXEN_WSL_DZN_ICD` compile-def.
  **Consequence: any run that does not set that env var runs on lavapipe (llvmpipe), not dzn** —
  the brief's "the whole test estate runs on dzn" is therefore conditional on the ICD env var.
- **The lane shell has no `DISPLAY` / `WAYLAND_DISPLAY`.** WSLg is live (weston running,
  `/mnt/wslg/runtime-dir/wayland-0` present, Xwayland on `/tmp/.X11-unix/X0`), but a dispatched
  agent inherits neither variable. A windowed run must set `DISPLAY=:0` (X11/Xwayland) or
  `WAYLAND_DISPLAY=wayland-0` with `XDG_RUNTIME_DIR=/mnt/wslg/runtime-dir`. **A windowed target
  launched without these fails at window creation, not at extension negotiation** — a plausible
  alternative origin for the controller's evidence.
- dzn advertises **no** `VK_EXT_surface_maintenance1` (instance) and **no**
  `VK_EXT_swapchain_maintenance1` / `VK_KHR_maintenance6` (device); lavapipe advertises all three.
  Both node filters drop them correctly, so this is survivable — but it means the dzn path runs
  with a different extension set than every lavapipe-based test.
