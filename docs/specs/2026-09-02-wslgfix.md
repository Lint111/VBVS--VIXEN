## 4. Fix — commit `d50d282f`

Five files, all cited above. The fix targets F1/F2/F3/F4 (the real fail-silent defects) and adds
the dzn-caps clamping the brief asked for.

**Honest negotiation (F1/F2/F3).** New `VulkanDevice::NegotiatePresentQueue(VkSurfaceKHR)`
(`VulkanDevice.cpp:399-455`) queries `vkGetPhysicalDeviceSurfaceSupportKHR` per queue family and
selects a family proven to support BOTH graphics and present. On failure it names the gap — GPU
name, family count, and the split between graphics-capable and present-capable families — so
"cannot present at all" is distinguishable from "can present, but not on a graphics family".
`vkGetPhysicalDeviceSurfaceSupportKHR` is a `VK_KHR_surface` **instance-level** entry point, so it
is callable before the logical device exists; this is what makes an honest negotiation possible at
all under the existing `instance → device → window → swapchain` graph topology
(`application/main/source/graph/BuildUIGraph.cpp:35-75`).

`graphicsQueueWithPresentIndex` now starts at `kPresentQueueNotNegotiated` (`VulkanDevice.h:66-68`)
instead of being seeded from `graphicsQueueIndex`, so `HasPresentSupport()` reports false until a
real surface proved otherwise rather than being unconditionally true.

`SwapChainNode` (`SwapChainNode.cpp:106-118`) calls the negotiation with the surface it just
created and reports what actually failed; its previous message claimed a presentation check that
never ran.

**Loud failure when presentation is requested but unsupported (F4, 0ej).**
`DeviceNode.cpp:293-319`: a requested-but-unadvertised `VK_KHR_swapchain` now throws at device
creation, naming the GPU and its advertised extension count, instead of a warning that yields a
device with a null `vkCreateSwapchainKHR` discovered much later at `ui_swapchain` compile. All
other requested extensions stay best-effort exactly as before.

**dzn-caps robustness.** `VulkanSwapChain.cpp`: the requested extent is clamped into
`[minImageExtent, maxImageExtent]` (VUID-VkSwapchainCreateInfoKHR-imageExtent-01274) and the image
count into `[minImageCount, maxImageCount]` at BOTH ends (the previous code clamped only the
maximum, so a driver reporting `maxImageCount < minImageCount+1` produced a request below the
minimum). Both negotiated values are now logged. Present-mode selection already only ever chose
from the queried `presentModes` list, so **FIFO-only drivers already worked** — no change was
needed there, and none was made.

### Regression surface of the semantic change, analysed while the families cannot run

The one behavioural risk this fix carries is that `HasPresentSupport()` changed from
*unconditionally true* to *true only after a real surface proved it*. A caller that consulted it
BEFORE negotiation would now see `false` where it previously saw `true`. That surface is closed:

1. **`HasPresentSupport()` has exactly one consumer** — `PresentNode.cpp:82`. (grep over all
   `.cpp`/`.h`: the only other hits are the declaration and definition.)
2. **`PresentNode` never appears without `SwapChainNode`.** All five graphs that construct a
   `PresentNodeType` — `BuildUIGraph`, `BuildRenderGraph`, `BuildInstancingDemoGraph`,
   `BuildFanInDemoGraph`, `BuildAutoSyncDemoGraph` — also construct a `SwapChainNodeType`. There is
   no graph in the tree that presents without a swapchain, so negotiation always precedes the query.
3. **Headless / offscreen graphs are unaffected**, because they contain no `PresentNode` at all —
   they never call the changed predicate.
4. **No test asserts on the changed semantics**: grep for `HasPresentSupport`,
   `GetGraphicsQueueHandle`, `NegotiatePresentQueue`, or `graphicsQueueWithPresentIndex` across
   every `tests/` directory returns nothing.
5. Even in the impossible case, `PresentNode` degrades safely rather than crashing: a `false` result
   falls through to the optional `PRESENT_FUNCTION` input slot (declared nullable,
   `PresentNodeConfig.h:151`) and throws a named error if neither yields a function.

This is a reachability argument, **not** a substitute for running the families — it bounds what the
families would be checking, so the re-dispatch knows where to look first if any of them do go red.
